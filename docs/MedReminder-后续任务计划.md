### 1.6 权限卡点击的根因与修复（`50c32d6`）

> **⚠️ 2026-09-17 更正：本节的结论不完整，只算对了一半。**
> 真正让权限卡「点了没反应」的根因是 **Capacitor 插件的 JS 从未被加载**（见 §3.5），
> 导致 `MedNotify.native` 恒为 `false` —— 整个应用一直跑在**浏览器降级模式**，
> 本节讨论的原生分支代码**从来没有被执行过**。
> 下面保留当时的分析（"不该砍掉申请路径"这个判断本身没错，只是没触及真问题）。

**根因是我上一轮的判断错了，不是 Android 的限制。**

上一版代码是：

```js
if (notifyPerm === 'denied' && native) {
  MedNotify.openSettings()...   // 直接跳设置，不再尝试申请
  return;
}
```

理由写的是「已被拒绝时系统不会再弹授权框，再调 requestPermission 是无效的」。**这个前提过于绝对。**

Android 官方文档说的是：用户在弹窗选「不允许」，与「在系统设置里手动关闭」，**效果相似**（都收不到通知）。但文档讲的是**行为效果**，**不等于"再请求时也不会弹窗"** —— 手动关闭相当于 revoke，**多数设备上重新申请仍会弹出授权框**。

于是上一版**把唯一一次能直接授权的机会砍掉了**。秦老师遇到的现象正好对上：双清后（权限处于"未决定"）能弹窗授权；手动关闭后代码直接跳设置，**根本没试过申请**。

**改法 —— 两段式：**

1. 点击 → **先真正调一次 `requestPermission()`**
2. 拿到 `granted` → 完成；否则 → 跳系统设置页（唯一 100% 有效的路径）

两条路都走通：能弹窗的设备一次点击就成功；不弹窗的设备落到设置页。

**另加两项：**

- **`appStateChange` 回到前台立即重查权限** —— 此前只靠 5 秒轮询，最坏要等 5 秒，用户会以为"改了没用"；而且 App 在后台时 JS 定时器本就被系统暂停，"回到前台"这个时机比轮询更准。
- **DEBUG 卡新增「上次点击权限卡：…」** —— 权限跳转是唯一没法远程验证的环节，把每步结果直接显示出来，出问题能一眼定位，不用来回猜。

**验证**：17/17 用例通过（在 `vm` 里跑源码真实文本），核心断言是「**必须先调用 `requestPermission`**」；另含「跳转失败不能变成点了没反应」「`prompt`/`unsupported`/`unknown` 都不误判为已授权」。

### 1.7 权限卡点击的第二次修复（`1841e63` · v1.1.2，2026-09-17）

**反馈**：「通知关闭以后，点击不弹出重新授权的。」

**根因：我把 `requestPermissions()` 的返回值当成败判据，而这个判据本身是错的。**

插件源码 `LocalNotificationsPlugin.requestPermissions()`：

```java
if (Build.VERSION.SDK_INT < TIRAMISU || getPermissionState(LOCAL_NOTIFICATIONS) == GRANTED) {
    resolve({ display: getNotificationPermissionText() });   // ← 不弹任何框
} else {
    requestPermissionForAlias(LOCAL_NOTIFICATIONS, call, "permissionsCallback");  // 只有这里才弹
}
```

即 **Android 13 以下永远不弹授权框**；13 以上若权限已是 `granted`（只是关掉了 App 总开关或本通知渠道）也不弹。**「没弹框」是预期行为，不是故障。**

而 v1.1.1 的写法是：

```js
if (p === 'granted') { notifyPerm='granted'; render(); toast('通知已开启'); return; }
... openSettings()
```

渠道被关时 `p` 正是 `granted` → 代码立刻宣布「通知已开启」并把卡片撤下，**既不弹框也不跳设置**。用户看到的就是「点了没反应」，而问题其实还在（5 秒轮询复检发现仍收不到，卡片又冒出来）。

**改法 —— 每一步都回到真实状态复检：**

| 步骤 | 行为 |
|---|---|
| `probe()` | 本就能收 → 只说明，不做多余动作 |
| ↳ 确实收不到 | `requestPermission()` —— 能弹框的设备在这一步就解决 |
| ↳ `probe()` 复检 | 仍不可用 → `openSettings()`（唯一 100% 有效的路径） |
| ↳ 跳不过去 | 写出失败原因 + 手动路径，**绝不「点了没反应」** |

另新增 `permBlockReason()`：把「权限被拒 / App 总开关已关 / 「服药提醒」渠道被关闭」分开显示 —— 三层开关对应三种不同的用户操作，笼统说「通知未开启」用户不知道关哪一层。

**`openSettings()` 同时加固**（本项目自研插件没有 JS 包装）：

- 优先取原生注入的 `Capacitor.Plugins.AppSettings`
- 若只有 `PluginHeaders` 里有它 → `Capacitor.registerPlugin('AppSettings')` 建代理兜底
- ★ 返回值从布尔改为 `{ok, reason}` —— 跳不过去时必须能告诉用户为什么
- 浏览器模式明确说明「无法跳系统设置」，不再静默

**诊断行扩展**（这类问题难定位，全因缺可观测信息）：

- 已注册插件：…
- **原生桥接：已注入 N 个插件头 / 未注入 —— 原生调用会失败**（用 `Capacitor.PluginHeaders` 判断）
- 跳设置插件：已注入 / 代理兜底可用 / 不可用
- **系统：Android X（可弹授权框 / 不弹授权框，只能跳设置）**

**验证**：49/49 通过。核心断言是「申请返回 granted 但复检仍不可用 → 必须跳设置，且**绝不置 `notifyPerm='granted'`**」—— 正是本次修复的点。

## 2. ✅ P1 · D-1 存储静默失败与无上限 —— **已完成**（`1f8df0c`）

> **这是当前代码里唯一会静默丢用户数据的地方，比崩溃更糟 —— 用户以为记录还在，其实最近的改动早已没了。**

**原证据**：

| 位置 | 问题 |
|---|---|
| `app.js:43` | `try { localStorage.setItem(...) } catch (e) { /* ignore */ }` —— 配额满时**一句话都不说** |
| 单一 key `medreminder.v1` | 全部数据塞一个 JSON |
| 全局 | `S.doses` **只增不减**，无任何清理 / 归档逻辑 |

### 2.1 实际实现与原计划的差异

| 原计划 | 实际做法 | 为什么改 |
|---|---|---|
| 第二步「按天清理（建议 90 天）」 | **不做自动清理**，改为**用户手动 + 自选保留期**（90 / 180 / 365 / 不清理） | 保留期是使用者的决策，不该由代码替他决定。**先让问题可见，比先删数据安全** —— 原计划的风险提示里也是这么写的 |
| 只在今日页顶部显示告警 | **今日页 + 记录页都放** | 用户可能整天停在今日页打卡，只在记录页提示等于没提示 |
| 文案「存储已满，新记录没有保存成功」 | 追加「**之前的记录没丢**」 | `setItem` 是**原子**的：失败不会写坏已有数据，磁盘上仍是上一次成功的完整版本。不说清这点，用户第一反应是「我的记录全没了」 |

### 2.2 三项落地内容

1. **失败可见（核心）**
   - `isQuotaError()` 识别三种跨实现命名（`QuotaExceededError` / `NS_ERROR_DOM_QUOTA_REACHED` / `code 22` / `1014`），并**区分「配额满」与「其他失败」** —— 两者的用户指引不同
   - 失败 → `storageError` 状态 → 跨页红色告警卡；**写入恢复后告警自动撤下**
   - 点告警卡**直达导出备份**：数据正在丢，第一优先是把已有记录抢救出来，而不是让用户自己去找入口
2. **容量可见** —— 记录页 `STORAGE · 本地存储` 卡：已用 KB / 5 MB + 占用条 + 天数条数。三档配色：`<70% 绿 / 70–85% 橙 / ≥85% 与写失败 红`
3. **清理能力（逃生通道）** —— 四档保留期，**默认停在「不清理」且确认键禁用**
   - 预览与实际删除**共用同一套判定**，保证「看到的数字」就是「真的会被删的」
   - **今天的记录永不清理**（它是当前排程的依据，删了 App 立刻错乱）；未来日期同样不删（防时钟漂移误删）
   - 清理时同步回收**孤儿 `notified` 标记**，否则 `doses` 删了体积也降不下来
   - `boot` 时自动跑 `gcNotified()`：纯垃圾回收，不碰任何用户可见数据

### 2.3 实现上踩到的两个坑（已处理）

- **`save()` 会在 `render` 过程中被调用** → 直接 `render()` 会递归。改为 `setTimeout` 排队 + `storageRefreshQueued` 标志防重入。失败状态持续时不再重复排队（告警已在界面上，重绘无意义）；**恢复后再次失败仍能重新点亮，不会永久哑掉。**
- **告警卡在两个视图各出现一次** → 用 `id` 会产生**重复 id**。改用 `data-storage-fix` + `document` 事件委托，顺带解决「重建 `innerHTML` 后绑定丢失」。

## 3. ✅ G-1 · 拍照打卡 —— **已完成**（`e74fa49` · v1.1.0）

> 秦老师要的是：**用拍照卡住打卡这个动作**。注意目标**不是"防遗忘"** —— 拍照发生在打卡那一刻，
> 而打卡本身就意味着你已经想起来了。它防的是**假依从**：现在通知上的「已服用」一秒就能点掉，
> 没吃药也能清掉提醒，App 还记一笔已服用。这比漏服更难发现 ——
> **漏服至少记录是空的，假依从连数据都是假的。**

### 3.1 三个设计决策

| 决策 | 做法 | 理由 |
|---|---|---|
| **拍不了怎么办** | **可跳过，但留痕**（标「未拍照」+ 计入跳过率） | 已拍板方案 B。现实中拍不了的场景很多（在外面 / 开会中 / 药盒没带 / 光线太暗 / 存储满 / 相机权限被误关 / 老人不会用相机）。硬拦会让这些用户只能强停 App，**数据直接断掉，比不强制更糟**。跳过率本身就是要观察的数据，不该一开始就锁死 |
| **哪些入口要拍** | **5 个全部**：今日页打卡 / 药卡点击打卡 / 提前服用 / 提醒弹窗 / **通知快捷按钮** | 通知那个是关键 —— 如果它不拍照，它就是一条绕过拍照的捷径，「强制」直接形同虚设 |
| **识别做到哪一档** | 本轮只做 **L0（拍到了就算）** | L1 质量校验（拒纯色/全黑/过糊）与 L2 感知哈希防重复留到下一批。判断依据见调研 §9.2：**宁可放行，不可误伤** |

### 3.2 技术要点

- 新增 `www/js/photo.js`（照片能力层，与 `notify.js` 同定位：原生差异收在一层，app.js 只管流程）
- `resultType: Uri` + `quality 60` + `width 1024` + `correctOrientation: true` + **`saveToGallery: false`**
  → **不需要任何存储权限**（走 Intent 调系统相机，不是自己开摄像头）。`AndroidManifest` 权限清单确认未新增
- 落盘优先 `Filesystem.copy`（不过 JS 层），失败退回 `readFile → writeFile` —— 路径格式在各平台接受度不一致，**两条路都走通，不赌**
- 照片存 `Directory.Data` 私有目录，**绝不进 localStorage**：压缩后一张 base64 约 110–270 KB，5 MB 上限只够 18–45 张，一天三次药 6–15 天就满
- **`appRestoredResult` 兜底**（Capacitor 官方明文要求）：拍照会启动独立 Activity，系统可能在过程中杀掉本 App。进拍照前把「这次要打卡哪些剂量」写进独立 key，恢复时接上。**不处理会同时丢照片和打卡**
- Esc 关掉拍照框会清掉该标记 —— 否则下次启动会被误当成「拍照途中被杀」而自动补打一次

### 3.3 与已有功能的一致性（这三条不做，前面的工作会白费）

- **存储卡纳入照片占用** —— 不并进来，D-1 那张卡显示的「已用」就是错的，而它的全部意义是让容量可见。现在分开列「记录 X KB + 照片 N 张 Y KB」
- **清理旧记录时同步回收孤儿照片**（只删没有任何记录引用的文件）—— 否则照片一直占着空间，D-1 的体积治理等于没做
- **备份格式 `BACKUP_VERSION` 保持 1 不变**：只加了 `photo` / `photoSkipped` 两个字段，旧备份没有这两个字段也完全兼容，导入校验不受影响
- 相机不可用（浏览器预览）时**直接放行且不计跳过** —— 那是环境不支持，不是用户偷懒，混进跳过率会让指标失真

### 3.6 拍照落盘失败的修复（`aec25da` · v1.1.3，2026-09-17）

**反馈**：「拍照显示的是没能拍照，parent folder doesn't exist。」

**注意这个信号**：错误来自 Filesystem —— **相机这一环已经通了**（照片拍出来了，走到了落盘），
说明 v1.1.1 的插件加载修复生效。问题在落盘：**我们从没创建过 `DATA/photos` 这个子目录。**

**源码级根因**（`@capacitor/filesystem`）：

| 方法 | 父目录不存在时 | 位置 |
|---|---|---|
| `writeFile` | reject **`Parent folder doesn't exist`** —— `recursive` **默认 false** | `FilesystemPlugin.java:110-113` |
| `copy` | 抛 `The parent object of the destination does not exist` —— **根本不读 `recursive`** | `Filesystem.java:135-137` |
| `mkdir` | 目录已存在时抛 `DirectoryExistsException("Directory exists")` | `Filesystem.java:83-85` |

实际链路正好解释了那句报错：`copy` 因父目录不存在失败 → 退回 `readFile`（成功，因为
`directory` 为 null 时 path 按 `file://` 解析）→ `writeFile` 也失败 → 抛出的就是它。

**改法**：

1. `ensureDir()`：`mkdir({path:'photos', directory:'DATA', recursive:true})`
   —— **已存在（抛 `Directory exists`）视为成功**；成功后缓存 `dirReady`；
   其它失败不阻断（`writeFile` 带 `recursive` 还能兜一次）
2. `persist()`：`ensureDir` → `copy`（最省内存）→ 失败退回 `readFile + writeFile({recursive:true})`
3. ★ **两条都失败时把两条原因都拼进错误信息**（`copy: … / write: …`）——
   否则真机上只能看到笼统失败，排查又得靠猜

**验证 26/26**（fs 桩严格按上面读到的 Java 语义实现，不是想当然）：

- **A 组复现原故障**：不建目录时 `copy` 抛父对象不存在、`writeFile` 抛的**正是真机那句**
  `Parent folder doesn't exist` —— 证明桩与现场一致
- B 修复后 `take` 成功、文件真落在 `DATA/photos`、内容走 `copy` 路径
- C 第二次拍照不重复 `mkdir`（`dirReady` 缓存生效）
- D `mkdir` 报「已存在」时仍成功
- E `copy` 失败 → 退避路径成功，且确实带上了 `recursive`
- F 两步都失败 → 错误信息同时含两条原因
- G/H 回归：取消 → `cancelled`、无插件 → `unsupported`、`src()/dirStats()/gc()` 正常

> ⚠️ **经验复用**：这轮 gc 那两条一开始也 FAIL，原因是**我的 fs 桩没实现 `deleteFile`**，
> `fs().deleteFile(...)` 抛 TypeError 被 gc 的兜底 catch 吞掉 → 返回 0。**源码没错。**
> 规则：**报 False 时先原样打印桩/检查串与源码对比，别急着改源码。**

### B-1 snooze 篡改计划时刻 + 越界钳制

**证据**：`app.js:697`、`app.js:1046` —— 两处都是 `ds.time = Math.min(1439, ds.time + 10)`。

**两个问题**（第二个是核实中新发现的，比审查意见说的更严重）：

1. **越界钳制**：23:55 snooze → `1445` 被 `Math.min(1439, ...)` 钳成 **23:59**。语义错乱：用户以为延后 10 分钟，实际只延后 4 分钟。
2. **⚠️ 篡改了计划时刻本身**：`ds.time` 是**计划服药时刻**，不是"下次响铃时刻"。snooze 一次，这条剂量在排程列表里的**显示时刻就被永久改掉**（08:00 → 08:10），**原始计划时间丢失**。snooze 三次就偏 30 分钟。这不是边界问题，是数据正确性问题。

**改法**：snooze 不应写 `ds.time`。应新增独立字段（如 `ds.snoozeUntil`）记录"下次响铃时刻"，`tick()` 判断时用 `snoozeUntil || ds.time`，排程表**始终显示原始计划时刻**。

**验收标准**：
- 用例：08:00 剂量 snooze 一次 → `ds.time` **仍为 480**（原计划时刻不变）、`snoozeUntil` 为 490
- 用例：23:55 snooze → 不再被钳到 23:59（应跨到次日 00:05，或明确提示"已过零点，不再顺延"——见 Q2）
- 用例：连续 snooze 3 次 → `ds.time` 始终不变

**工作量**：低（改 2 处 + `tick()` 一处判断 + 迁移旧数据时忽略 `snoozeUntil`）

### B-2 跨天剂量被丢弃

**证据**：`app.js:158-165` —— `if (t >= 1440) { dropIds.push(d.id); return; }` 然后从 `S.doses` 里 `filter` 掉。22:00 打卡 + 8 小时间隔 → 次日 06:00 那次**不会排**。

**⚠️ 修正审查意见**：审查说"不会有任何提示"——**不准确**。`takenToast`（`app.js:182`）会明确告知：
```
已记录 22:00 · 某某药，后续 2 次已顺延，3 次越过零点不再提醒
```
即"行为可能不合期望，但**用户知情**"。所以这不是静默 bug，是**设计取舍**。

**改法取决于产品决策**（Q3），三条路：
- (a) **维持现状**：跨天不排，仅靠 toast 告知。最简单，但 8 小时药晚打卡就永远少一次。
- (b) **补到次日**：写入 `S.doses[明天]`——但会与"明天首次打卡才排程"的模型冲突，可能重复。
- (c) **明确告知 + 引导**：保持不补，但在今日页**常驻**一条提示（而非只 toast 一闪而过），说明"有一次排到次日已跳过，建议明早补记"。

**我的建议**：先 (c)。(b) 会动到核心排程模型，风险高、收益不确定。

**验收标准**（按选定方案）：
- (c)：跨天 drop 后，今日页出现常驻说明条；关闭后当天不再弹

## 5. 🔵 P3 · 功能缺口

### F-1 间隔仅支持整数小时

**证据**：`app.js:625` `clampStep()` 限定 `1 ≤ stepVal ≤ 24`（整数小时）；`app.js:621` 预览按 `stepVal * 60` 生成。

**审查意见准确**。「每天三次」「饭前 30 分钟」这类医嘱确实表达不了。

**⚠️ 但注意一个既有约束**：这套排程是**打卡制的滚动间隔**（不是固定时刻表）——`app.js:114` 从打卡时刻起按 `step` 滚动排。所以"饭前 30 分钟"本质是**固定时刻表**语义，与当前模型不同源。见 Q4。

**两种做法**：
- (a) **低风险**：步进粒度从 1 小时细化到 **30 分钟**（`stepVal` 改为以分钟存、步进 30）。改动小，覆盖"每 8 小时""每 1.5 小时"。
- (b) **高风险**：新增"指定时刻"模式（如 08:00 / 12:30 / 18:00 三个固定点）。这是**第二种排程模型**，与打卡制并存会让 `rollForward` 顺延逻辑变得很复杂——固定时刻**不应顺延**。

**我的建议**：先做 (a)。(b) 单独立项，不要和"提醒逻辑"这批混在一起改。

### F-2 记录页无按药筛选 / 无单药依从率

**⚠️ 修正审查意见**：审查说"缺少聚合统计"——**不准确**。记录页**已有**两个聚合（`app.js:527-532`）：`STREAK 连续打卡` 与 `ADHERENCE 本月依从率`。

**真正缺的**是：① **按药品筛选**；② **单药依从率**（现在只有一个全局值）。审查意见的"这种药的依从率"这个说法是对的。

**顺带发现一个真问题（新）**：`calcAdherence()`（`app.js:582-595`）只统计 `taken` / `skipped`，而**我一轮加的批量补记 `btnMissAll` 会把所有漏服一键标成 `taken`** → **一次点击即可把依从率刷到 100%**。这个指标因此不可信。建议：统计时**把 `makeup: true` 的剂量与真实打卡区分**（`makeUp()` 已写入该标记），例如依从率只算真实打卡，补记单列。

**验收标准**：
- 用例：批量补记 3 次后，依从率**不因此上升**（或明确拆成"真实打卡率 / 含补记"两个数）
- 用例：按药筛选后，只统计该药剂量

### F-3 授权引导时机

**证据**：`askNotify()` 调用点只有三处（`app.js:367` 权限卡、`:403` 单药打卡、`:416` 全量打卡）。**「添加药品」时不引导**。

**审查意见部分成立**：打卡时**已**引导，但用户"设完药 → 还没打卡"这段空窗期不知道自己收不到提醒。

**改法**：`openSheet` 保存药品成功后，若是首次添加且未授权，主动调 `askNotify()`。

**工作量**：低。**验收**：首次添加药品后弹授权（若 `prompt` 状态）；已 `granted`/`denied` 时不重复骚扰。

### 12.1 B-1 snooze 篡改计划时刻（`708ed49`）—— 数据正确性

改它等于把排程表上的显示时间永久改掉（08:00 → 08:10），原始计划时间丢失、连延三次偏 30 分钟；
23:55 延后还会被钳到 23:59（用户以为延 10 分钟、实际 4 分钟）。

**改法**：新增独立字段 `d.snoozeUntil`（下次响铃时刻）+ `dueAt(d)` 统一取值，**`d.time` 永不被 snooze 改写**；
`snoozeDose()` 统一两处入口；跨零点**明确拒绝**并提示，而不是悄悄钳；
`tick()` / `isMissed()` / `nextPending()` / `syncNotifications()` 全部改按 `due` 判定；
排程行给延后的剂量加「延后至 HH:MM」标记（否则用户会以为"延后了怎么列表没变"）。

## 13. 2026-09-17 通知重复弹出（v1.2.1）

### 反馈

> 「测试通知，点一次给我出来6个。」

### 根因（插件源码级）

`www/js/notify.js` 的 `cancelAll()` 旧实现：

```js
function cancelAll() {
  if (!NATIVE || !scheduled.length) return Promise.resolve();   // ← 问题在这里
  var ids = scheduled; scheduled = [];
  return LN.cancel({ notifications: ids }).catch(function () {});
}
```

`scheduled` 是个**内存变量**。App 被系统杀掉 / 用户上划关闭，它就归零；
于是**插件持久化存储里的那些通知，再也没有任何代码去清**，全成了僵尸。

僵尸的下场写在插件源码里 —— `LocalNotificationRestoreReceiver.onReceive`
（注册在 `BOOT_COMPLETED` / `LOCKED_BOOT_COMPLETED` / `QUICKBOOT_POWERON`）：

```java
if (at != null && at.before(new Date())) {
    // modify the scheduled date in order to show notifications that would
    // have been delivered while device was off.
    long newDateTime = new Date().getTime() + 15 * 1000;
    schedule.setAt(new Date(newDateTime));
}
```

**手机每次开机，插件都会把存储里所有「关机期间本该响」的通知改成「开机后 15 秒」再响一遍。**
攒了几条，开机 15 秒后就一起弹几条 —— 这就是「一次冒出来一堆」。

另一处独立缺陷：`test()` 用的是 `1 + Math.floor(Math.random() * 2000000000)`。
随机 id 意味着**测试通知越点越多，而且事后谁也认不出来、取消不掉**。

### 修法

| # | 改动 | 作用 |
|---|---|---|
| 1 | `cancelAll()` 改为**先问插件要权威清单**（`LN.getPending()`）再全部取消；拿不到时退回自建台账 | 不再依赖内存状态，跨会话也能清干净 |
| 2 | `purge()`：启动时清排程 + 清通知栏；`doSync` 会等它完成 | **App 每次打开都从干净状态开始** —— 开机时插件就没有东西可「复活」 |
| 3 | `clearDelivered()`：回到前台清掉通知栏里已显示的 | 息屏期间被攒下、唤醒时一起弹出的那批，用户一进 App 就被清掉 |
| 4 | `test()` 改**固定 id + 先取消再登记** | 点多少次都只有一条测试通知 |
| 5 | 已排通知 id **落盘**（`notifPending.v1`） | `getPending` 不可用时的兜底 |
| 6 | `doSync` **串行化**（`syncBusy` / `syncQueued`） | 两次排程交错时不再各排一份、留下没人认领的僵尸 |
| 7 | DEBUG 卡加「系统排程 N 条 · 通知栏 N 条」+「清除全部提醒通知」按钮 | 这类问题没有数字只能靠猜，现在用户自己也能一键清 |

### 验证 48/48（`tests/notify.spec.js`，可重跑）

桩严格按插件 Java 语义写（`schedule` 按 id 覆盖、`cancel` 同时删存储、`getPending` 返回存储内容、
**以及原样实现 RestoreReceiver 的「at 已过 → now+15s」**）：

- **A 组先复现原故障**：存储里 6 条过期通知 → 模拟开机 → 6 条被改成「15 秒后响」→ 推进 16 秒后
  **一起投递出 6 条**。这组就是用户看到的现象，证明桩与现场一致
- B 修复后：`purge()` → 存储 0 条 → 开机复活 0 条
- C 跨会话：会话 1 排 3 条 → App 重启（内存台账归零）→ 会话 2 排 2 条 → **系统里只有 2 条**
- D **测试通知幂等**：连点 5 次只有 1 条（固定 id）；并**反证**旧写法会留 5 条
- E 并发 sync：连发三次 → 最终只剩最后一轮的 2 条，无中途遗留
- F/G 台账落盘、`clearDelivered` 不动闹钟、`purge` 全清、`stat` 报数
- H 启动顺序：不 await 的 `purge()` 与紧随其后的排程不互相踩
- I 降级：浏览器模式全部安全降级；插件没有 `getPending` 时退回台账也能清干净
- J 源码级断言（**剥离注释再查**，防止改回旧写法）

> ⚠️ 本批我自己错了一次：断言直接 `fireNow()` 期望 6，但 `boot()` 刚把时间改成「15 秒后」，
> 此刻当然还没到点 → 得到 0。**测试要模拟时间推进，不能只看断言写得漂不漂亮。**

### 14.1 F-5 相机没生效的真正原因（`ae` → `4ae283b`）


### 14.2 F-6 药品删除的两个真问题（`4ae283b`）

### 14.3 F-4 固定时刻排程（`08a4435` · v1.3.0）

数据模型：`med.mode` = `'interval'`（**缺省即此**）| `'fixed'`；`med.times` = 分钟数组。
旧数据没有 `mode` 一律视为 interval，备份格式不变。

| | interval（滚动间隔） | fixed（固定时刻） |
|---|---|---|
| 生成时机 | **打卡时**才生成当天的 | **不等打卡**：启动 / 跨天 / 保存后预生成 |
| 顺延 | 跟随实际打卡时间 | **绝不顺延**（晚吃两小时不该把晚上那次也推后） |
| 跨天丢弃 | 可能发生（§B-2 有提示） | 不会（时刻固定） |

三条实现要点：

1. **fixed 不能等打卡才生成** —— 否则第一个时刻的提醒永远不会响。
   共三处入口调 `ensureFixedDoses()`（幂等，已有就不重复生成）。
2. **不顺延的实现** = `markTaken` 在 fixed 模式直接跳过 `rollForward`。
3. **改设置后重排**（`rebuildTodayDoses`）要先**撤掉旧时刻的系统通知**，
   且**已打卡的记录一律保留**（哪怕新时刻表里没有它）—— 那是发生过的事实。

界面：药品浮层加「服药方式」切换；固定模式用原生时间选择器逐行编辑时刻，
事件走委托、改某一行不重排列表（会打断输入）。

### 14.4 F-7 自动本地备份（`aca3b93` · v1.4.0）

**本 App 的 Manifest 里没有任何存储权限** → Android 10+ 的 scoped storage 下
写公共目录（Documents / Download）**会失败**。所以：

| 顺序 | 目录 | 取舍 |
|---|---|---|
| 1 | `Directory.External` | app 专属外部目录。**无需权限**；「清除应用数据/缓存」**不会**碰它；电脑 USB 可见 |
| 2 | `Directory.Data` | 私有目录，一定能写。兜底 |

⚠️ **卸载 App 会连 `Android/data/<包名>` 一起删** —— 这条**写在记录页卡片上**，
不含糊：换机 / 重装前必须先用「导出备份」另存一份到别处。

工程约束：**防抖 3 秒**（`save()` 调用极频繁）+ 切后台 `flush()`；
**写失败一律不影响打卡**；内容用与手动导出**完全相同的 `buildBackup()` 格式**
（恢复流程直接读回）；保留 `latest.json` + 最近 14 份日备份。

## 15. 2026-09-21 通知无声修复（v1.4.1 · `01e8e2a`）

### 反馈

> 「现在只有震动，没有声音了，是为什么？」
> 随后补充：「它之前是默认声音，然后就没有，我给它指定了一个声音就可以了。」

**后半句直接指向了根因** —— 用户手动指定铃声就好了，说明「默认音」这条路本身是坏的。

### 根因（代码级确证）

`notify.js` 创建渠道时传了 `sound: 'default'`，而插件的实现（`NotificationChannelManager.java`）：

```java
String sound = channel.getString(CHANNEL_SOUND, null);
if (sound != null && !sound.isEmpty()) {
    Uri soundUri = Uri.parse("android.resource://" + context.getPackageName() + "/raw/" + sound);
    notificationChannel.setSound(soundUri, audioAttributes);
}
```

它把 `sound` 当成 **`res/raw` 下的资源名**去拼 URI。而本 APK **从来没有 `res/raw` 目录**
（已核实 `android/app/src/main/res/` 只有 drawable/layout/mipmap/values/xml）
→ 拼出的 `android.resource://com.medreminder.app/raw/default` **永远解析不了**
→ 渠道在系统设置里显示「默认」看着正常，**真播时找不到文件 → 静音**。
震动是独立的 `enableVibration(true)`，所以表现正是「只有震动、没有声音」。

**为什么"之前有声音"**：v1.1.1 之前插件 JS 没加载，通知跑在**浏览器降级模式**
（页面内弹窗 + Web Notification）—— 那些有声音。v1.1.1 起真正走系统渠道，就一直静音。**时间线吻合。**

### 修法（一处，且刻意最小）

创建渠道时**不传 `sound`** → 插件不调 `setSound()` → 渠道使用**真正的系统默认通知音**。

★ **故意没有换渠道 id**：一开始改成 `doses2` 并删旧渠道来强制重建，
但秦老师**已经手动把 `doses` 渠道的声音修好了** —— 换 id 会把他刚做的设置丢掉。
所以保持 `doses` 不变：**尊重用户已完成的修复**。
（Android 8+ 渠道属性不可变，改代码改不动已创建的渠道；新装 / 重装 / 清数据的设备会新建，从一开始就是对的。）

### 顺带修：构建日期改为自动注入

第一次出包时文件名还是 `-2026-09-17.apk` —— 因为 `APP_BUILD` 是 `app.js` 里一个**手写常量**，
改版本号时很容易忘记改日期（这次就忘了）。
`build-apk.sh` 现在**一律取系统当天日期并回写进 `app.js`**，
文件名 / App 内 DEBUG 卡 / 原生 `versionName` 三处必然一致。

### 验证

`tests/notify.spec.js` 52/52（新增 4 条防回归断言：不传 `sound`、渠道 id 不变、
`importance` 必须为 5、无 `deleteChannel`）；`tools/verify-apk.py` 加 2 项，合计 64 项。

> **可复用的教训**：往第三方插件传参数时，**先看它 Java 侧怎么解析这个值**
> —— 参数名看着通用，语义却可能是平台特定的。与 §13（Camera 的 `source` 必须全大写）同类，**这已经是第二次**。

### 17.1 H-1 —— 固定时刻「只改时刻」不重排

**根因**：`saveMed` 里的判定写成 `if (modeChanged || intervalChanged)`。而固定模式下
`intervalChanged` 带 `!isFixed` 前置恒为 false、`modeChanged` 又要求模式真的变了 ——
所以「只改时刻」两个条件都不成立 → **今天页与系统通知仍是旧时刻，要等次日才生效**，
用户会以为"改了没用"。

**修法**：把判定抽成纯函数，显式包含「时刻变了」这一支：

```js
function needRebuildDoses(prev, next) {
  if (prev.mode !== next.mode) return true;                              // 模式换了
  if (next.mode === 'fixed') return !sameTimes(prev.times, next.times);  // 固定模式：时刻变了吗
  return prev.interval !== next.interval;                                // 间隔模式：间隔变了吗
}
```

抽成纯函数的两个理由：① 可被单测（见 17.4）；② **防止将来又漏掉某一种变化** ——
H-1 就是这么漏掉的。`rebuildTodayDoses` 的语义一字未动：**已打卡的记录一律保留**。

### 17.8 v1.4.3 —— 真机反馈的三条修复（`b2489aa` / `c0b51e3`，2026-09-24）

秦老师验收时反馈：**点「新建药品」有时没反应 → 于是连点 → 卡死；没有侧滑返回，只能杀 App 重开；

| 反馈 | 根因 | 修法 |
|---|---|---|
| 点「新建药品」**有时没反应** | `render()` = `renderToday(); renderMeds(); renderRecords();` —— **一次重建三个视图的 innerHTML**。手指落下（pointerdown）到 click 之间只要重绘一次，**正在点的元素就被换掉**，click 落在已脱离文档的节点上、静默失效。而 `refreshPerm` **每 5 秒**轮询、签名一变就 `render()`，这个重绘**不受用户控制** | 药品页改**事件委托**（只绑一次、天然免疫重绘 —— 项目里存储卡早就用这招）；`refreshPerm` 有浮层时不再重绘；`openSheet` 防重复打开 |
| **没有侧滑返回**，只能杀 App | 全项目**搜不到一处** `App.addListener('backButton')` —— 返回键从来没被处理 | 新增 `handleBackButton()`，优先级抽成纯函数 `backAction(s)`：**可关浮层 → 编辑浮层 → 切回「今天」→ 退出 App**。⚠️ 提醒弹窗 / 确认框**不许**被返回键抹掉（要"吃掉"返回、不退出），否则误按一次就退出 App。Esc 改为复用同一套 `closeTopDialog()` |
| 药品页**一长串同名药** | 连点「保存」= 多次「新增药品」（`S.meds.push`）；同一浮层会话里名字不被清空 → 每条一模一样 `c0b51e3` | `sheetSaveBegin/Reset` 防重入：一次浮层会话只允许保存一次 |

**顺带**：`sw.js` 的 network-first 补 **1.5s 超时** —— 网络「半死」时不再卡在加载；
超时先用缓存撑起界面、网络那份回来后再悄悄回填；网络正常时立刻返回、不白等（有用例守着）。

### 18.3 无打包器的代价：加一个模块要做**四**件事

1. 写 `www/js/core/<名>.js`，用 `export`

## 19. 2026-09-28 两个新功能（v1.4.8 · `5561819`）

秦老师提的两条：

> 一个是我希望在页面上滑动能直接切换三个选项卡，另外一个是在进入这个页面，
> 它这个 History 这个卡片，它如果是时间长了以后会非常非常的长，能不能把它合并一下，

### 19.1 左右滑动切换选项卡

**判定抽成纯函数** `swipeTarget(cur, dx, dy)`（与 `backAction` 同一套路：DOM 事件在调用方
拍好再传进来）→ 判定矩阵可以直接单测，不必造触摸事件。**三条否决各有用例**：

| 否决 | 为什么 |
|---|---|
| 位移 < 60px | 手抖不是手势 |
| 竖向位移 ≥ 横向 | **让滚动赢** —— 不判这条，一边上下滚一边手一歪就会莫名换页 |
| 已在两端 | 停住不绕回（绕回会让人晕） |

**接线**：监听挂 `#main`（不会被重建，绑一次就够）、`passive: true` 不阻断滚动；
浮层开着 / 双指（缩放）/ 落在浮层或输入框上的触摸 → 都不参与。

⚠️ **不设 `touch-action`** —— 设了会把双指缩放一起废掉，而 `capacitor.config.json` 里的
`zoomEnabled: true` 是刻意开的。`tests/swipe.spec.js` 里立了一条断言盯住它。

### 19.2 「记录」页历史收进二级菜单

页面只留「**摘要 + 最近 3 天 + 查看全部历史(N 天)**」，完整按天列表进 `dlgHistory`。

| 决定 | 理由 |
|---|---|
| 摘要报**总量**（共 N 天有记录 · 合计 M 次服药） | 用户想知道的是"我坚持得怎么样"，不是"昨天吃了没" |
| 筛选 chips **页面与菜单里各一份** | 页面上那份还在驱动「本月依从率」（按药看依从率有意义）；菜单里那份是因为菜单盖住了页面、够不着 |
| 筛选改 **document 级事件委托**，并**删掉旧的直接绑定** | 菜单内容会重绘，绑在元素上的 click 会随 innerHTML 重建而失效（"点了没反应"，本项目踩过一次）；旧绑定不删会双触发 |
| `dlgHistory` 加进 `closableDialogs()` | 否则**返回键关不掉**，只能点关闭按钮 |
| 列表区 `.dlg-scroll` 自带 `max-height` | `.dlg` 没有 max-height、`.dlg-wrap` 也不滚，不设上限会把对话框撑出屏幕 |

## 20. 2026-09-29 H-3 —— 备份导入 doses 侧校验（v1.4.9）

### 20.1 问题（逐行核实过）

`parseBackup()` 原来对 `o.data.meds` 逐条严验，对 `o.data.doses` **只查了
`typeof === 'object'`** —— 于是下面这些都放行，并在**导入成功之后**炸在别处：

| 坏数据 | 放行后的后果（已核实到具体行） |
|---|---|
| `doses` 值是字符串/数字/对象/`null` | `S.doses[k].some(...)`（`hasTaken`）/ `.forEach` → **TypeError，记录页整页白屏** |
| `doses` 整体是数组 | 同样是上面的崩溃路径 |
| 日期键不是真日期（`2026-9-1` / `2026-02-30`） | 排序、`adherenceStats` 按 `'YYYY-MM'` 取前缀过滤全错 |
| 剂量 `time` 越界 / 非数字 | `minToStr`、排程比较得到荒谬结果 |
| 缺 `id` / `medId` | 照片回收、依从率按 `undefined` 归组 |
| `status` 是未知值 | 既不算已服也不算待服，**静默丢出统计** |
| 体积无上限 | 一份巨型 JSON 能塞爆 localStorage 配额 |
| 重复导入 | 见 §20.3 |

### 20.2 修法

新增 `dosesInvalid(doses)`（与上方 `meds` 的 `badMed` 写法对称、同样返回
"有问题"的布尔值）+ `isDateKey(k)`（用**日期回写比对**而非正则，才拦得下
`2026-02-30` / `2025-02-29`），并给 `parseBackup` 加**体积上限**。

三条刻意的边界（写进测试钉住）：

- **`medId` 允许指向已删除的药品** —— 历史记录里"药删了、记录还在"是
  **刻意保留的"已发生的事实"**（工程纪律 §4.5），不能因为对不上 `meds` 就拒；
- **`time` 的合法边界是 `0` 与 `1439`**，两端都放过；
- **`takenAt` 允许 `null`（未服）或数字（时间戳）**，其它类型一律可疑。

体积上限取 **2 MB 字符**（即使按 UTF-16 的 2 字节/字符也才 4 MB，低于 5 MB 预算
并留余量）；正常用户一个月的记录约 **27 KB**（测试实测），离上限两个数量级。

### 20.3 关于"防重复导入"

`applyRestore` 的语义是**整体覆盖**（`S.doses = d.doses`），所以同一份备份
导入两次**不会翻倍**——这一点本身是对的。真正要防的是"把导入当合并"的误用，
因此本条以**源码级断言**钉住"存在重复识别/提示路径"，而不去改覆盖语义。

## 21. 2026-09-29 真机反馈：拍完照又让再拍一次（v1.4.10 · `80f1e30`）

### 21.1 反馈（秦老师原话）

> 「我现在装的版本还是这个 1.4.6，9 月 28 号的版本。今天中午又出现了一个原来有的 bug：
> 就是我已经点击拍照记录了以后，然后它又给我提示我还需要点击拍照，这次我放弃了，
> 但是它拍照已经成功了。我想是不是有卡顿或者什么情况，你检查一下这个东西。」

### 21.2 根因（已逐行核实）

**用户的"卡顿"直觉是对的，但机制不是卡顿 —— 是 App 被杀。**

相机在本项目里是**独立 Activity**（Capacitor Camera 的实现方式）。低端机 / 内存紧张时，
系统会在相机 Activity 运行期间**把本 App 的进程杀掉**来回收内存。Capacitor 会把结果
暂存起来，重启后通过 `appRestoredResult` 事件回放（`retainUntilConsumed=true`，事件不丢）。

于是出现一个**几分钟的空窗**：

| 时刻 | 系统里发生的事 | 用户看到/做的事 |
|---|---|---|
| T0 | 用户点「打卡」→ `photoGate` 弹框 → `savePendingShot` 留痕 → 拉起相机 Activity | 拍照框 |
| T1 | 系统为省内存**杀掉本 App** | 相机界面（不受影响） |
| T2 | 用户拍完确认，相机 Activity 结束 | 回到"桌面"，点开 App |
| T3 | **App 冷启动**：`todayDoses()` 还是空的 → 显示「今天还没打卡」+ 打卡按钮 | **"没成功"** |
| T4 | 用户又点「打卡」 | **又弹出一个拍照框**（"又提示要拍照"） |
| T5 | `appRestoredResult` 到达 → 照片落盘 + 打卡完成 | "拍照已经成功了" |

T3 是万恶之源：**冷启动时界面完全没有"正在恢复"的迹象**，用户只能得出"刚才白拍了"的结论。

### 21.3 附带发现：一个静默丢打卡的 bug（比主 bug 更隐蔽）

顺着这条路径读 `resumeShot` 时发现：`kind:'one'` 分支**拿错了 id**。

`photoGate` 的调用方有**两种约定**（读源码核实，非推断）：

| 调用点 | 传的 `doseId` 实际是 | 出处 |
|---|---|---|
| `bindToday` 里 `$$('[data-checkin]')` | **`med.id`**（药品 id） | `app.js` line 837 |
| 「下一次」按钮 | **`med.id`** | line 872 |
| 记录页 / 别的入口 | **`dose.id`**（剂量 id） | line 1525 / 2360 |

而旧 `resumeShot` 只按 **dose.id** 处理：

```js
var l = todayDoses(), ds = null;
for (var i = 0; i < l.length; i++) if (l[i].id === p.doseId) { ds = l[i]; break; }   // ← med.id 永远匹配不上
if (!ds || ds.status !== 'pending') { render(); return; }                             // ← 静默 return
```

**后果**：单药用户（今天只有一种药 → 走 `data-checkin` 的 med.id 路径，正是秦老师的场景）
在被杀-恢复时会**静默丢掉这次打卡** —— 照片落盘了，剂量没生成，界面一刷新又回到"未打卡"。
这解释了为什么这个 bug"原来就有"且反复出现。

### 21.4 修法（四处，都刻意最小）

1. **新增 `restoringShot` 状态位**；`photoGate` 开头加**两道闸**：
   - `if (restoringShot)` → 拒绝，提示"上次的拍照还在处理"；
   - `if (pendingShot)` → 拒绝，提示"拍照正在进行中"。
     （否则第二次调用会**覆盖 `pendingShot`**，让真正要恢复的那次彻底对不上号 ——
     这是"又让我拍一次"的放大器。）
2. **`resumeShot`**：进入即 `restoringShot = true; render();`，结束复位（**失败路径也复位**，
   不永久锁死）；`kind:'one'` 改为走 `checkIn(p.doseId)`，失败再按 `medId` 回退补挂照片。
3. **`renderToday`** 加「正在恢复上次拍照…」诚实态 —— 不再让用户误以为白拍了。
4. **`boot()`** 检测未消费留痕 → 进恢复态；**30 秒兜底**自动解锁 + 清留痕
   （防止异常残留把用户永久锁在恢复态）。

> 设计取舍：**不用"恢复中禁用按钮"，而是改文案 + 拒绝新会话。** 因为禁用按钮在
> 慢设备上会让用户以为"App 卡死了"；诚实文案 + "请稍等片刻，不用再点一次"
> 才是对用户正确的心智模型。

### 22.2 方案：`harness/` —— 一个入口、一份报告、一个退出码

```
harness/
  harness.py        统一入口（调度 + 汇总 + 判死）
  gates.py          16 个关口的定义（只描述"跑什么、怎么判"）
```

```bash

python harness/harness.py --only spec  # 只跑某类
python harness/harness.py --selftest --selftest-e2e   # 自检 harness 自己
```

### 22.3 ★ 三条硬规矩（都是本项目用血换来的）

1. **跳过 ≠ 通过。** `SKIP`（如"没有 APK"）显式标注、报告末尾单独列出、**绝不计入通过**。
2. **假绿必须挡住。** spec 判据是 **M>0 且 N==M**：
   - 共 0 条断言 → **判 FAIL**（不是"空集通过"）；
   - 抠不到汇总行 → **判 CRASH**（套件自身出错，不是 PASS）。
3. **环境问题自成一类。** 退出码 **2** = 跑不起来（命令找不到 / 子进程被禁），
   与"代码有问题"（1）严格区分 —— 对应沙箱里 `spawnSync` 报 `EBUSY` 被误当成用例失败那次。

### 22.4 ★ 诚实标注：有假阳性的检查标 ADVISORY，不当闸门

`check-module-imports.py` 报的 5 处，逐条核实**全是假阳性**：

| 报的名字 | 真实来源 |
|---|---|
| `$`（schedule.js） | 正则 `/^(\d{1,2}):(\d{2})$/` |
| `Android`（app.js） | 注释里的「Android 13」 |
| `backup`（backup.js） | 正则 `/^backup-\d{8}\.json$/` |
| `A`/`Za`/`z0`/`cancel`/`exist`（photo.js） | 内嵌 vendor 压缩码 |
| `quot` | 单双引号交替的字符串 |

**一个有假阳性、永远红的检查等于没有检查** —— 红久了就没人看了（"狼来了"）。
故标为 `ADVISORY`：执行、留输出、**不影响退出码**。
> 这条本身也是设计原则：**与其把有假阳性的工具塞进闸门，不如诚实标注它的可信度。**

### 22.5 ★★ 两层自检（凭什么相信 harness 自己）

一个"汇总算错"的 harness **比没有 harness 更危险** —— 它会谎报全绿。

## 23. 2026-09-29 自动验证：挂到 git pre-commit（`6f36188`）

### 23.1 需求

秦老师：「能不能直接加一个状态机，每次修改完直接自动跑？」
追问后确定：**提交时自动跑（git pre-commit）+ 失败拦住提交**。

### 23.2 为什么选 pre-commit 而不是"存盘就跑"

| 方案 | 问题 |
|---|---|
| 存盘就跑（watcher） | 全量 19 秒，边写边跑很吵；且后台常驻进程在受限环境不稳 |
| **提交时跑（选中）** | 只在「落定」那一刻把关，不打断写代码的过程；成本 = 每次提交多 ~19 秒 |
| 手动敲命令 | 又要"记得敲" —— 正是要消灭的东西 |

> 核心判断：**「改完不跑」的根因是"要靠自觉"，那就把它从"自觉"变成"物理上做不到"。**

### 23.3 实现（3 个文件）

| 文件 | 进 git？ | 作用 |
|---|---|---|
| `harness/pre-commit.sh` | ✅ | **真正的逻辑**（找仓库根/python、跑 harness、判定、给排查指引） |
| `harness/install-hooks.sh` | ✅ | 安装/卸载/切换模式（幂等） |
| `.git/hooks/pre-commit` | ❌ | 仅 3 行**转发器**（`.git/` 不进版本库，随时可重建） |

```bash
bash harness/install-hooks.sh              # 全量（16 关口，~19s）
bash harness/install-hooks.sh --fast       # 快速版（syntax+apk，~3s）
bash harness/install-hooks.sh --uninstall  # 卸载
```

### 23.4 ★ 三条设计取舍（都写进注释了）

1. **故意留逃生门**：`SKIP_HARNESS=1 git commit` / `--no-verify`。
   > 一个**没有逃生门**的闸门，会逼人在急的时候去**删 hook 文件** ——
   > 那比绕过更糟（改回来很难记得）。**有逃生门但默认开着，才是能长期活下去的闸门。**
2. **逻辑放仓库里，hook 只做转发**：`.git/hooks` 不随仓库走，换机/重 clone 就没了
   → **新环境第一件事是跑一次 `install-hooks.sh`**。
3. **环境问题（退出码 2）也拦，但明说"这不是代码的错"**，并给修环境的指引。

### 23.5 耗时拆解（决定要不要用 `--fast`）

| 关口 | 耗时 |
|---|---|
| `syntax` | 1.3 s |
| `apk` | 2.0 s |
| 13 套 spec | **~17 s**（瓶颈：13 次 Node 冷启动） |
| 合计 | ~19 s |

> ⚠️ **若 19 秒让你开始想用 `--no-verify`，那就该改装 `--fast`** ——
> **一个你愿意用的 3 秒闸门，胜过一个人人都绕过的 19 秒闸门。**

### 23.6 实测（两次真实 `git commit`）

| 场景 | 结果 |
|---|---|
| 正常提交 | 16 关口全过 → `✅ 验证通过（19s）—— 继续提交` → **提交成功** |
| 注入语法错误 | `syntax` + `apk` 两关口 FAIL → `❌ 本次提交已被拦下` → **`git log` 确认该提交未产生** ✅ |

（测试后 `util.js` 按 MD5 校验逐字节还原，无残留。）

**① `getPending()` 在鸿蒙上不可用**（影响最大）

- ⚠️ 陷阱：我们判断的是 `typeof LN.getPending !== 'function'` ——
  鸿蒙上**函数存在、只是调用被拒** → 该判断不成立，靠的是后面那层 `.catch`
- **移植时要做**：台账每次 schedule 后**立即持久化**；考虑"保守清场"；真机再验

**② `EXTERNAL` 静默落沙箱**（已据此改了主项目）

- `DOCUMENTS` 才是真·用户可见（`/storage/Users/currentUser/Documents/`）
- **已改** `backup.js`：`['EXTERNAL','DATA']` → `['DOCUMENTS','EXTERNAL','DATA']`（**v1.4.11**）
- **双端无损**：Android 无存储权限 → 写 DOCUMENTS 直接失败 → 自动退 EXTERNAL（行为不变）
- **教训**：「不报错」≠「落点正确」

### 28.2 方案的核心判断：**只收口，不抽象**

现状只有 Android 一个真实平台（鸿蒙还在等 AGC 审批）。此时设计「平台接口」是**凭空猜**，必然猜错。

`isMissed()` 内部拿 `nowMin()` 比较，**只对今天安全**：
反例 —— 昨天 23:00 的剂量，今天 00:10 看，`nowMin() - dueAt = 10 - 1380` 是**负数**，
复用会把它误判成「未到时间」（漏服凭空消失）。已在 spec 的 C 节钉死。

**③ 「已跳过」不计入依从率分母。**
跳过是用户主动的（如医嘱停药），算进去会**冤枉人**；单列出来让医生自己判断。
→ `1 服 + 1 跳过 = 100%`，有 spec 佐证。

**另外**：分母为 0 时依从率是 **`null` 而不是 0** ——「这几天没数据」和「一次都没吃」是两回事，
显示 0% 会冤枉人。界面上渲染成「—」。
