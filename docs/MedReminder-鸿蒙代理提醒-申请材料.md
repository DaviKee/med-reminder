## 0. 先看这一节：有个可能**不用等 8 天**的办法

> 📄 **详细操作步骤见单独的《`MedReminder-自动签名操作卡.md`》**（精确到菜单项 + 故障排查表）。

官方 FAQ《HarmonyOS 权限分类、受限权限审批前调试方法》原文（🔵）：

> 「**本地可以使用调试 Profile 提前获取相关受限权限进行应用调试。**」

另有官方论坛答疑解释机制（🔵）：
> 「**调试签名模式下部分系统策略检测会被放宽或走本地调试白名单**……而切换为 Release Profile 时，系统会严格校验 AGC 后台配置与签名文件的映射。」

### ⚠️ 但要先说明不确定性

「自动签名代申请」官方是写在**受限权限（ACL）**章节里的；
而**代理提醒走的是「开放能力管理」，不是「ACL 权限」页签** ——
所以**自动签名能不能拿到代理提醒的配额，文献上没有明确答案。**

### ✅ 所以：**先花 10 分钟试一下**（成本极低，成了就省 8 天）

```
1. 打开 DevEco Studio 打开工程：spike/harmony-test/openharmony
2. File → Project Structure → Project → Signing Configs
3. 勾选 ☑ Automatically generate signature
   （如果是 HarmonyOS 工程，还要勾 ☑ Support HarmonyOS）
4. 点 "Sign In" → 浏览器登录华为账号 → 授权 → 回到 IDE
5. 点 Apply / OK，等它自动生成调试证书与 Profile
6. 重新编译 → 安装 → 跑探针 → 看 hilog 里 publishReminder 是否还报 1700002
   （复测命令见 §5.4；跑之前**必须先卸载旧应用**，否则签名不同会装不上）
```

**结果处理**：
- ✅ **不报 1700002 了** → 开发调试阶段畅通，**正式发布前再走 §3 的正式申请**即可

## 2. ★ 申请原因文案（可直接复制）

**这是本次申请最关键的产出** —— 审核员就是靠这段文字 + 截图判断"该不该给你这个能力"。

### 2.1 精简版（用于申请框内填写，约 150 字）

```
MedReminder（药准时）是面向老年人及慢病患者的服药提醒工具，本地优先、无账号、数据不上传。
用户多为记忆力下降的老人，不会主动打开应用、也不会保活后台进程，因此普通依赖应用存活的本地
通知在应用被系统回收后即失效，直接导致漏服。
需接入代理提醒，把服药提醒托管给系统服务：即使应用被清理或退出，仍能在设定时间准时提醒；
并使用稍后提醒与排除日期能力，支持延后服药或跳过某次。
本应用为纯健康工具类应用，由用户主动设置提醒、仅提醒其本人服药，不发送任何营销或广告推送。
```

### 2.2 完整版（如需补充说明/备注栏）

```
【应用定位】
MedReminder（药准时）是一款面向老年人及慢病患者的服药提醒工具。产品坚持本地优先：
无需注册账号、不采集个人信息、数据全部保存在用户本机，不上传服务器。

【用户与痛点】
目标用户是记忆力下降的老年人及其家属。这类用户有三个特点：
1. 不会主动打开应用查看，完全依赖系统主动提醒；
2. 不会管理后台进程，应用常被系统回收或被家人清理；
3. 漏服的后果严重（如降压药、降糖药漏服会直接影响健康）。

【为什么必须使用代理提醒】
普通本地通知依赖应用进程存活，一旦应用被系统回收或被清理，提醒即失效。
实测中我们也验证了这一点。而代理提醒由系统服务托管，应用被清理后仍能准时触发，
这是解决"漏服"的唯一可靠方案。

【具体使用方式】
1. 用户为每种药设置服药时间，支持两种排程：每日固定时刻、按小时间隔（如每 8 小时一次）；
2. 到达时间由代理提醒弹出通知，用户可直接在通知上选择"稍后提醒"（稍后 30 分钟）；
3. 支持"排除日期"，用于用户主动跳过某次服药；
4. 提醒全部由用户本人设置，仅用于提醒其本人按时服药。

【合规承诺】
本应用为纯健康工具类应用，不涉及营销推送、不做电商促销、不发送广告，
不会将代理提醒用于任何商业化或骚扰用户的目的。
```

> 💡 **写作要点**（供以后修改参考）：
> ① 先说**用户是谁、痛点是什么**（老人 + 漏服后果）
> ② 再说**为什么别的方案不行**（普通通知依赖进程存活）
> ③ 最后**承诺不滥用**（这是审核最关心的）

## 5. ⚠️ 审批通过后必须做的事：手动签名（不做仍报 1700002）

**官方原文**（🔵）：
> 「此时，**调试和发布应用必须重新生成 Profile 文件并使用手动签名**。」

社区补充（🟡）：
> 「开通能力后，**原有的 Profile 文件并不会自动更新能力项**。必须在 AGC 的"证书、Profile 管理"页面中，
> 针对该 Profile **重新关联生成并重新下载 `.p7b` 文件**。」
> 「如果 Profile 文件中未包含 `ohos.permission.PUBLISH_AGENT_REMINDER` 的受限能力授权，
> **即使应用代码配置了权限，安装到真机或模拟器后系统依然不会给予配额**。」

### 5.1 签名文件四件套

| 文件 | 生成/获取方式 |
|---|---|
| `.p12`（密钥库） | DevEco 生成（File → Project Structure → Signing Configs → 新建） |
| `.csr`（证书请求） | 同上，由 `.p12` 导出 |
| `.cer`（数字证书） | 用 `.csr` 在 AGC 申请 |
| **`.p7b`（Profile）** | ⭐ **在 AGC 生成 —— 必须重新生成，确保包含新申请的能力** |

### 5.2 顺序（**别搞反**）

```
① 先在「开放能力管理」把代理提醒**配置好**（申请通过 + 勾选开关 + 保存）
        ↓  ← ⚠️ 官方原话：「配置的开放能力信息会写入 Profile，建议在申请 Profile 前完成配置」
② 再去「证书、Profile 管理」**重新生成并下载 .p7b**
        ↓
③ 把 .p12 / .cer / .p7b 配到工程的 Signing Configs
        ↓
④ 编译 → 安装 → 跑探针验证
```

> ⚠️ **官方注意项**：「**修改开放能力配置后，原有 Profile 将失效**，请重新下载 Profile。」
> 所以每次动过开放能力开关，都要重新走一遍 ②。

### 5.3 怎么确认 Profile 里真的有这个权限

🟡 社区建议：**用文本工具或签名解析工具查看重新生成的 `.p7b`**，
检查其中的 `restricted-permissions` 或 `app-capabilities` 字段
是否**明确包含** `ohos.permission.PUBLISH_AGENT_REMINDER`。

### 5.4 复测命令（通过后跑一次确认）

```bash
D="/d/Program Files/Huawei/DevEco Studio"
HDC="$D/sdk/default/openharmony/toolchains/hdc.exe"

# 先卸载（签名变了，覆盖安装会失败）
"$HDC" -t 127.0.0.1:5555 uninstall com.medreminder.spike
# 编译 + 安装（见 spike/harmony-test/probe/README.md）
# 然后清日志 → 启动 → 等 26s → 读探针输出
"$HDC" -t 127.0.0.1:5555 shell hilog -r
"$HDC" -t 127.0.0.1:5555 shell aa start -b com.medreminder.spike -a EntryAbility
sleep 26
"$HDC" -t 127.0.0.1:5555 shell hilog -x -T SPIKE-REMINDER
```

**看这一行**：`1) publishReminder OK  id=xxx` ← 出现这行就说明通了。
（现在它是 `1) publishReminder FAIL code=1700002`）

> ⚠️ **复测时顺带复验 `repeatInterval` / `repeatCount`**（API 26 新增的周期倒计时参数）：
> 上一轮实测它报 `401 参数错误`，但当时**没有授权**，无法区分是「没权限」还是「参数组合不对」。
> 授权到手后复测一次，把《OpenHarmony7-特性研究》§7 第 4 项关掉。

### 5.5 权限声明与通知授权（代码侧两件事，缺一个都发不出提醒）

**① `module.json5` 声明权限** —— 🟢 本地 SDK `PermissionDefinitions.json` 实测：
`ohos.permission.PUBLISH_AGENT_REMINDER` 是 **`system_grant` / `normal` 级**
（**声明即自动授予**，不需要运行时弹窗，也不需要 `reason`/`usedScene`）：

```json
"requestPermissions": [
  { "name": "ohos.permission.PUBLISH_AGENT_REMINDER" }
]
```

（spike 工程里已按此声明，`bm dump` 实测 `grantStatus=0`。）

**② 请求通知授权** —— 用户没开通知开关时 `publishReminder` 报 **`1700001`（Notification is not enabled）**，
首次启动要调 `notificationManager.requestEnableNotification()` 弹窗请求：

```ts
import { notificationManager } from '@kit.NotificationKit';
notificationManager.requestEnableNotification().then(() => {
  // 用户同意 → 可发布提醒
}).catch((err: BusinessError) => {
  // 用户拒绝 → 引导去设置开启（拒绝后弹窗不再弹，只能设置页开）
});
```

## 7. 万一申请没通过怎么办（退路已想好）

**不是死路。** 退路是「**WebView 内排程 + 应用存活时发通知**」（≈ 我们 Android 现在的方式）：

| | 代理提醒（若通过） | 退路方案 |
|---|---|---|
| 应用被杀后 | ✅ **仍准时提醒** | ❌ 提醒失效 |
| 应用在前台/后台存活时 | ✅ | ✅ |
| 实现成本 | 低（原生支持稍后提醒/排除日期） | 中（要自己做排程与清场） |
| 用户体验 | 好 | **降级**（用户清理应用后会漏提醒） |

→ 所以这是**体验降级，不是功能归零**。但**越早申请越好**，因为它决定要不要为退路额外做设计。
