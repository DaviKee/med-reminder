## 0. 先说三条结论

> **⚠️ 2026-09-16 需求澄清（重要，请先读这一节）**
>
> 秦老师明确了意图：**用拍照作为打卡的必要动作，强制把"拍照"和"吃药"绑在一起**。
> 这修正了本文档下面基于推测写的部分判断，我重新组织一下：
>
> **这个方向是有道理的，但作用机制要讲准确。**
>
> 它防的**不是"忘记吃药"**，而是**"随手把提醒划掉、假装吃过了"**。
> 现在通知上有一个「已服用」按钮，一秒就能点掉 —— 用户可以在完全没吃药的情况下
> 把它清掉，App 还会记一笔"已服用"，依从率显示 100%。
> **把拍照设为打卡的必要条件，就让"清掉提醒"这件事有了成本。**
> 这才是这个功能真正的价值，而且是个真问题 —— 属于「假依从 / false compliance」，
> 不是「遗忘」。
>
> 所以下面的 §1 依然成立（拍照不解决"忘"），但**结论要改**：
> 如果痛点是"随手划掉提醒"，那这条路线值得做，见 **§9 修订方案**。

**① 拍照防不了"遗忘"，但能防"假装吃过"。** 见上面说明。

**② 技术上可行，但存储是硬约束，而且会引爆一个已知的严重问题。** 现有数据全在 `localStorage`（约 5 MB 上限），一张压缩后的打卡照片 base64 约 110–270 KB —— **只能存 18–45 张，每天三次药的话 6–15 天就满**。更糟的是 `save()` 在配额满时是**静默失败**的（这是已识别的 D-1 问题），照片会把"数据悄悄丢失"从"理论上会发生"变成"一周内必然发生"。

**③ 强制方案有一个必须先定的设计点：拍不了的时候怎么办。** 见 §9.4。这一个决定直接决定用户会不会绕过你的产品。

## 1. 需求逻辑先对齐（这一节最重要）

你的原话是：「**这样能保证每次吃药不会被遗忘**」。但拍照的时机与这个目标之间有一道逻辑缺口：

| | 防遗忘需要的是什么 | 拍照实际给了什么 |
|---|---|---|
| 起作用的时间点 | **吃药之前** —— 提醒你该吃了 | **打卡之时** —— 你已经吃完了 |
| 机制 | 更强的提醒、更难忽略、他人介入 | 留痕、可追溯、可展示 |
| 对依从性的作用 | 直接提高（减少漏服） | 间接（事后压力），且会因增加摩擦而**降低打卡率** |
| 谁能受益 | 用户自己 | 照护者 / 医生 / 临床研究 |

**换个说法**：如果某天你真的忘了吃药，那天你也**不会**打卡 —— 于是也不会有照片。照片记录的是"你想起来的日子"，恰恰漏掉了"你忘掉的日子"。**漏服是无声的，照片对它无能为力。**

### 那拍照在什么场景下真的有价值？

它是有真实先例的，但价值点在别的方向：

- **临床/公共卫生领域的 DOT（Directly Observed Therapy，直接面视下治疗）** —— WHO 推荐用于结核病等，本质是让医护**看着**患者服药。近年有 AI 辅助的"视频 DOT"用摄像头做**服药核验**（如 AiCure 类产品）。
- 关键差别：那些场景里，**核验方是第三方（医生/研究方）**，目的是"确认患者真的吃了"。**不是为了帮患者记住吃。**

所以真正的问题不是"能不能拍"，而是：

> **Q1：你要的是"帮我别忘"，还是"留个证据给别人看"？**

这两条路的技术方案、成本、风险完全不同。**在这个问题有答案之前，后面的技术选型都是空转。** 我在 §5 给了三条路线，对应不同答案。

### 如果目标是"帮我别忘"，更该做的是

这些原计划里已有或成本更低，且**直击漏服**：

| 手段 | 为什么更有效 | 来源 |
|---|---|---|
| **漏服可见化** | 让"漏了"这件事被看见 —— 漏服现在已经是可见的了 | 已完成 `0e64fd1` |
| **时间窗**（如 8:00–10:00 内都算按时） | 单点时刻容易被错过，窗口容错更高 | 原计划 P2-2 |
| **升级通知**：漏服 N 次提醒照护者 | 把提醒延伸到"会催你的人" | 原计划 P2-3 |
| **补服次数上限** | 防止漏了之后乱补 | 原计划 P2-2 |
| 长按通知直接打卡（已有） | 降低响应成本 | 已实现 |

**一句话**：想减少"忘"，就去降低"想起"的成本、增加"忘记"的代价；而不是在"想起来之后"加一道手续。

## 2. 现状约束（决定了方案边界）

| 约束 | 现状 | 对拍照功能的影响 |
|---|---|---|
| **存储** | 全部数据在 `localStorage` 单 key `medreminder.v1`；**无容量上限保护**；`save()` 配额满时**静默失败**（`app.js:43`） | ⛔ **硬约束**。照片不能进 localStorage，且必须先解决静默失败 |
| **插件** | 只有 `@capacitor/app` + `@capacitor/local-notifications` | 需新增 Camera（+ 可能 Filesystem） |
| **无后端** | 纯本地，无网络服务 | 照片只能存本地，或由用户手动导出 |
| **备份格式** | `BACKUP_FORMAT = 'medreminder.backup'`，`BACKUP_VERSION = 1`（`app.js:725-726`） | 照片进不了现有 JSON 备份，**备份链路必须重新设计** |
| **导出** | JSON 备份（可完整恢复）+ CSV（给医生看） | CSV 可加"有无照片"列；但照片本身无法进 CSV |
| **Android** | `targetSdk 34`，debug 构建 | 权限与存储受 Android 13+/14 限制 |
| **现有权限** | INTERNET / USE_EXACT_ALARM / SCHEDULE_EXACT_ALARM / POST_NOTIFICATIONS / VIBRATE / WAKE_LOCK / RECEIVE_BOOT_COMPLETED —— **无 CAMERA** | Camera 插件默认**不需要** CAMERA 权限，见 §3.1 |
| **测试** | 无单测、无 CI，回归全靠手测 | 照片链路（权限/失败/迁移）回归成本高 |

## 3. 技术手段调研

### 3.1 获取照片的四种方式

| 方案 | 权限 | 体验 | 体积/风险 | 结论 |
|---|---|---|---|---|
| **A. `@capacitor/camera`（官方）** | **无需任何权限**（除非 `saveToGallery: true`） | 调用系统相机 App，体验原生 | 官方维护，成熟 | ✅ **正式方案推荐** |
| **B. 纯 Web `<input type="file" accept="image/*" capture>`** | 无 | 一般（部分 WebView 行为不一致） | **零插件、零依赖** | ✅ **原型验证首选** |
| C. `getUserMedia` 自绘相机 | 需 `CAMERA` 权限 | 可完全自定义 | 实现量大、要处理对焦/旋转/机型差异 | ❌ 收益不抵成本 |
| D. 社区/第三方插件 | 不定 | 不定 | 维护风险、升级断裂 | ❌ 不建议 |

**方案 A 的关键事实**（来自 Capacitor 官方文档）：

- `getPhoto(options)` 支持 `quality`(0-100)、`width`/`height`（最大边，等比缩放）、`correctOrientation`、`source`（Camera/Photos/Prompt）、`resultType`（Uri/Base64/DataUrl）、`allowEditing`、`saveToGallery`（默认 false）。
- **"The Camera plugin requires no permissions, unless using `saveToGallery: true`"** —— 因为它通过 Intent 启动系统相机 Activity，不是自己开摄像头。
- ⚠️ **一个必须处理的边界**：拍照会启动独立 Activity，**系统可能在拍照过程中杀掉本 App**。官方明确要求监听 `App.addListener('appRestoredResult')` 才能把照片数据拿回来。我们已经在用 `@capacitor/app`，具备条件，但**不处理就会丢掉这次打卡的照片甚至打卡本身**。
- 从相册选图在 Android 11+ 走系统 Photo Picker，也不需要读存储权限。

**方案 B 的价值**：一行 HTML、零插件、当天可跑。**用来回答"用户到底会不会拍"这个问题，性价比最高。** 缺点是不能作为长期方案（无法稳定拿到原始文件路径、WebView 差异）。

### 3.2 照片存哪里（含容量测算）

**先算清楚体积**，这是整个决策的核心：

| 环节 | 典型大小 |
|---|---|
| 手机原生照片（12MP JPEG q90） | 3–5 MB |
| 经 `width:1024, quality:60` 压缩后 | 约 80–200 KB |
| **转成 base64（×4/3）** | **约 110–270 KB** |
| Android WebView `localStorage` 单源限额 | **约 5 MB**（部分机型 10 MB） |
| **→ 可存张数** | **约 18–45 张** |
| 每天 3 次药 | **6–15 天就满** |
| 每天 1 次药 | 18–45 天 |

**结论：照片绝对不能进 localStorage。**

| 存放位置 | 权限 | 容量 | 卸载即清 | 其他 App 可读 | 结论 |
|---|---|---|---|---|---|
| `localStorage`（base64） | — | ~5 MB | ✅ | ❌ | ❌ **不可行** |
| **`Directory.Data` + `@capacitor/filesystem`** | **无需权限**（应用私有目录） | 设备可用空间 | ✅ | ❌ | ✅ **推荐** |
| `Directory.Cache` | 无需权限 | 同上 | ✅ | ❌ | ⚠️ 系统可随时清理，不适合长存 |
| 系统相册（`saveToGallery`） | 需存储权限 | 大 | ❌ | ⚠️ **可读** | ❌ 隐私差，不推荐 |
| `IndexedDB` | — | 较大 | ✅ | ❌ | ⚠️ 配额与清理策略不可控，不建议 |

**推荐结构**：

```
Directory.Data/
  photos/
    2026-09-16_0800_<doseId>.jpg     ← 压缩图（约 100–200 KB）
```

`dose` 记录里只存**相对路径字符串**（几十字节），不存 base64。这样 localStorage 的增量可以忽略不计。

> 显示时用 `Capacitor.convertFileSrc(uri)` 转成 `<img src>` 可用路径。

### 3.3 与现有备份/导出链路的冲突（容易被忽略）

这是**最容易被低估的工作量**。现有备份是"一个 JSON 装下全部数据"，可完整恢复。照片进来之后：

| 方案 | 效果 | 代价 |
|---|---|---|
| 照片**不进**备份 | JSON 备份仍可完整恢复"记录"，但**恢复后照片全丢** | 需明确告知用户；逻辑简单 |
| 照片**打包进**备份（zip） | 真正完整 | 需 Filesystem 打包 + `@capacitor/share` 分享；备份体积从 KB 涨到几十 MB；剪贴板主路径**彻底失效** |
| 照片**单独导出** | 备份仍是 JSON，照片另走一个"导出照片"流程 | 两个流程、两套心智模型 |

⚠️ 注意现有备份的一个设计前提：**「剪贴板是主路径」**（因为没有原生文件插件）。照片一进来，这个前提直接不成立 —— 几十 MB 不可能走剪贴板。**备份的产品设计需要重做。**

## 4. 风险清单

### 4.1 技术风险

| # | 风险 | 严重度 | 说明与对策 |
|---|---|---|---|
| T1 | **存储静默丢失** | 🔴 **致命** | 照片塞进 localStorage → 一周内配额满 → `save()` 静默失败 → **用户的服药记录一起丢**。对策：照片必须走 Filesystem；且**先做 D-1 存储治理**（`save()` 失败必须可见） |
| T2 | **备份链路断裂** | 🟠 高 | 见 §3.3。恢复后照片丢失会造成"我明明拍了"的信任崩塌 |
| T3 | **`appRestoredResult` 未处理** | 🟠 高 | 系统在拍照时杀掉 App → 照片与打卡同时丢。官方明确要求处理 |
| T4 | **权限被拒/无相机时阻断打卡** | 🟠 高 | 必须有不阻断的降级路径，否则用户直接无法打卡。**打卡是核心行为，不能被任何新功能挡住** |
| T5 | **EXIF 泄露** | 🟡 中 | 照片可能带 GPS、设备型号。`correctOrientation` 只处理方向，需主动剥离 EXIF |
| T6 | 内存与性能 | 🟡 中 | base64 大字符串在 JS 侧处理有峰值内存；列表渲染需用缩略图 |
| T7 | 迁移与兼容 | 🟡 中 | 老记录无 `photo` 字段 → 视为"无照片"，需保证向后兼容与 v1→v2 备份兼容 |
| T8 | 相机 App 不可用/被禁用 | 🟡 中 | 少见但存在（企业设备、精简 ROM） |

### 4.2 隐私与合规风险 ★ 单独成节，因为容易被当成"纯技术问题"

**先说一个关键判断：这个功能是否适用《个人信息保护法》，取决于你用它做什么、给谁看。**

**PIPL 第72条原文**：「自然人因个人或者家庭事务处理个人信息的，**不适用本法**。」

- ✅ **纯自己用 / 给家人用，照片永不出设备** → 大概率落在第72条豁免内，合规负担很轻。
- ❌ **一旦发生以下任一情形，就落入 PIPL 管辖**（照片涉及"医疗健康"，属**敏感个人信息**）：
  - 上架应用商店分发（你成为"个人信息处理者"）
  - 把照片给照护者看 / 导出给医生 / 任何对外提供
  - 未来接入任何云端

**若落入管辖，需要满足**（法条原文要点）：

| 条款 | 要求 | 对我们的具体含义 |
|---|---|---|
| 第28条 | 医疗健康属**敏感个人信息**；须有"特定的目的和**充分的必要性**"，并采取严格保护措施 | **"必要性"是最大的软肋** —— 若不用照片也能达成目的，收集照片本身就站不住脚（见 §1） |
| 第29条 | 处理敏感个人信息须取得**单独同意** | 不能混在总隐私政策里，要单独弹窗确认 |
| 第30条 | 还须告知**必要性及对个人权益的影响** | 要写清"为什么必须拍照""不拍会怎样" |
| 第55条 | 处理敏感个人信息须**事前做个人信息保护影响评估（PIA）**并记录 | 需要留档，不是写句话就行 |
| 第19条 | 保存期限应为**实现目的所必要的最短时间** | "永久保存所有照片"很难解释 |
| 第47条 | 个人有权**删除** | 必须提供"删除全部照片"入口，且要真删 |
| 第6条 | 遵循**最小必要**，不得过度收集 | 又一次指向"必要性" |
| 第51条 | 采取加密、去标识化等技术措施 | 至少要做到应用私有目录 + 不导出 |

**额外风险**：照片可能**拍到第三人**（家人、护士、诊室环境），那是别人的个人信息，你无权代为同意。建议默认引导"只拍药盒"，而不是"拍服药过程"。

### 4.3 体验风险 ★ 这节是我最想让你先看的两条

| # | 风险 | 说明 |
|---|---|---|
| U1 | **打卡率下降，依从性反而变差** | **最反直觉、也最重要**。这套 App 的排程是"打卡制"：不打卡 → 不排程 → 没有提醒。给打卡加一道拍照手续，**直接降低打卡率**。结果是为了提升依从性做的功能，**让依从性更差**。 |
| U2 | **老年用户门槛** | 原研究报告要求样本含 ≥2 名 60 岁以上。开相机、对准、对焦、弱光、手抖 —— 每一步都可能卡住。而他们恰恰是最需要服药提醒的人。 |
| U3 | **拍不了的现实场景** | 在外面、开会中、手边没药盒、单手抱孩子。必须有"跳过拍照"且**不惩罚**（不能因为没拍就让打卡失败）。 |
| U4 | **照片未必有核验价值** | 没有图像识别的前提下，照片只能证明"有个药盒"。人眼事后翻看几十张几乎一样的照片，信息量很低。若真要核验，需要 AI 识别能力 —— 那是另一个量级的项目。 |
| U5 | **隐私不安感** | 用户可能因为"要被拍照"而干脆不用这个 App。对一款本应无压力的工具，这是真实成本。 |

### 4.4 维护风险

| # | 风险 |
|---|---|
| M1 | 引入 2 个新插件（Camera、Filesystem），依赖面扩大，Capacitor 升级成本上升 |
| M2 | 无单测/无 CI，照片链路的权限、失败、迁移只能手测，回归成本高 |
| M3 | 备份/导出/恢复三条链路都要改，改动面比"加个拍照按钮"大得多 |

## 5. 三条可选路线（对应 §1 的不同答案）

### 路线甲：目标是「帮我别忘」→ **不做拍照**

改做提醒增强：时间窗、漏服升级通知、补服上限、照护者提醒。
**成本最低、直击问题、无隐私负担。** 建议优先考虑。

### 路线乙：目标是「留证据」→ 做**可选**拍照（推荐若确实要拍照）

- 拍照**可选**，永不阻断打卡
- `@capacitor/camera` + `Directory.Data`
- 只存缩略图（`width:1024, quality:60`），列表里显示小图
- 剥离 EXIF
- 提供"删除全部照片"入口
- **前置条件：D-1 存储治理必须先完成**
- 备份策略：照片**不进** JSON 备份，但需明确告知"照片不随备份恢复"

**工作量**：中高（拍照本身简单，**备份链路重做 + 迁移 + 失败路径**才是大头）

### 路线丙：先验证，再决定（**我的建议**）

**阶段 1（零成本，1 天）**：用 `<input type="file" capture>` 做一个**可选**拍照，照片只存内存/localStorage 里最多 3 张（够看效果就行），跑一周。
**判据**：你自己一周会用几次？

- 用不到 3 次 → **停。** 不必做完整功能。路线甲更值得投入。
- 经常用且觉得有价值 → 走路线乙，做正式实现。

这条路线的价值：**用一个下午的成本，避免几天的正式开发 + 长期的合规负担。**

## 9. 修订方案（2026-09-16：以"强制拍照打卡"为目标）

### 9.1 目标重新定义

| | 旧假设 | 秦老师澄清后的实际目标 |
|---|---|---|
| 要解决的问题 | 忘记吃药 | **随手划掉提醒、假装吃过** |
| 手段 | 提醒增强 | 让"清掉提醒"有成本 |
| 拍照的角色 | 证据（可选） | **打卡的必要动作（强制）** |

**为什么这个目标成立**：现在通知上带一个「已服用」按钮，**一秒就能点掉**。用户完全没吃药也能把它清掉，App 还会记一笔"已服用"，依从率显示 100%。这是**假依从（false compliance）**，比漏服更难发现 —— 漏服至少记录是空的，假依从连数据都是假的。

**强制拍照把"清掉提醒"从零成本变成有成本**，这一层是真实收益。

### 9.2 "简易识别"能做到什么、做不到什么（关键技术判断）

先说结论：**离线做不了药物识别，但做得了"防敷衍"。** 建议把目标定成后者。

| 档次 | 能力 | 可行性 | 判断 |
|---|---|---|---|
| L0 | **只要求"拍到了一张"** | 零成本 | ✅ 主力方案。仅此一条已足够改变行为 |
| L1 | **质量校验**：拒绝纯色/全黑/过糊/过暗 | 纯 canvas 采样算方差与边缘密度，**零依赖** | ✅ 建议加。防对着墙壁拍 |
| L2 | **防重复**：拒绝拿同一张旧图反复交差 | 感知哈希 pHash，约 50 行纯 JS | ✅ 建议加。防一次拍完重复用 |
| L3 | **识别"这是不是药盒"** | 需 ML 模型。**无网络、模型几 MB~几十 MB 要打进 APK**，且通用模型对药盒识别准确率不够 | ❌ 不划算，误判会拦住正常用户 |
| L4 | **人脸/服药动作识别** | 同 L3，且是"服药过程"视频级任务 | ❌ 同上 |

**⭐ 一个容易被忽略的强校验（推荐）**：**把当前时间要求出现在画面里**（比如要求拍药盒 + 旁边放手机/钟表，或要求拍屏幕上的时间）。理论上可伪造，但对"随手糊弄"的拦截力比图像识别强得多，成本却近乎为零。

**为什么不做 L3/L4**：这个项目**网络受限且无后端**，把模型塞进 APK 会让体积翻几倍；而识别错了会把"正常吃药的人"挡在打卡之外 —— **误伤的代价比漏放高得多**。

### 9.3 存储与备份（沿用前面结论，但现在它们变成必须解决的）

因为强制了，这两条**从"可选优化"变成"前置阻塞项"**：

1. **D-1 存储治理必须先做** —— 否则照片会把 `save()` 的静默失败从理论风险变成一周内必然事故。
2. **照片必须走 `Directory.Data`**（私有目录、免权限），绝不进 `localStorage`（18–45 张就满）。
3. **备份策略必须重新决策** —— 现有备份前提是"剪贴板是主路径"，几十 MB 照片让这个前提失效。

### 9.4 ⚠️ 唯一必须由秦老师拍板的设计点：拍不了的时候怎么办

**这一条决定用户会不会绕过你的产品，比识别算法重要一百倍。**

现实中拍不了的场景很多：在外面、开会中、药盒没带、手边没光、手机存储满、相机权限被误关、老年人不会用相机。

| 方案 | 行为 | 后果 |
|---|---|---|
| **A. 硬性阻断** | 不拍就不能打卡 | 拍不了时用户**只能强制停止 App 或卸载**。数据直接断，比不强制更糟 |
| **B. 可跳过，但留痕** | 能打卡，标记为「未拍照」并在记录里显式标出 | ✅ **推荐**。既保留了"默认要拍"的摩擦力，又不给用户"无路可走"的绝望 |
| **C. 可跳过，另需二次确认** | 加一道"确定不拍照？"确认 | 折中。摩擦更大，但可能被点习惯 |

**我的建议：B + 对"跳过率"做统计。** 如果某用户频繁跳过，那说明要么他不接受这个设计，要么场景确实拍不了 —— 这本身是有价值的数据。**用数据判断该不该收紧，而不是一开始就锁死。**

### 9.5 强制版的额外风险（前面没覆盖的）

| # | 风险 | 说明 |
|---|---|---|
| F1 | **打卡率下降 → 提醒排不出来** | 这套 App 是打卡制排程，打卡率直接决定依从率。强制拍照会降低打卡率。**这是"用真实性换完成率"的主动取舍** —— 可以做，但要看数据 |
| F2 | **老年人门槛** | 目标用户含 60 岁以上。开相机、对准、对焦、弱光都是障碍 |
| F3 | **照片存了但没人看** | 没有识别能力时，照片的价值主要在"拍摄这个动作本身"。要有心理准备：这些照片可能永远不会被回看 |
| F4 | **合规"必要性"要求更高** | 可选收集的"必要性"已经吃紧；**强制收集**更难辩护。纯自用可依第72条豁免，一旦上架/给别人看就必须做 PIA（第55条） |
| F5 | 前台提醒与拍照的交互 | 现在提醒弹窗有「已服用 / 稍后」。强制拍照后，"已服用"必须先拍照 —— 弹窗流程要重做，且要处理"拍照中弹窗被系统杀掉" |

### 9.6 建议的实施顺序

```

                                                     但「恢复后照片不回来」还没在 UI 上说清
④ L1 质量校验 + L2 防重复（可选增强）                 ⏳ 未做（本轮只到 L0）
⑤ 真机验收 + 观察一周"跳过率"                         ⏳ 待做
```

## 11. 第三方方案核实（2026-09-16）

秦老师提供了一份外部（Claude Code）方案，分三个递进层次。**核实结论：层次 1 与我方调研方向一致（两处细节需调整）；层次 2 在该插件上技术上不可行；层次 3 方向对但三处与已拍板决策冲突。**

### 11.1 层次 1「拍照打卡」—— 方向一致，两处细节要改

| 条目 | 核实结论 |
|---|---|
| 用 `@capacitor/camera` | ✅ 与 §3.1 的推荐方案一致 |
| 拍摄时压缩（`quality` / `width`） | ✅ 方向对。但 `quality:40 / width:800` **偏激进** —— 药盒上的药名小字可能看不清，而"留证"恰恰需要看清。建议 `quality:60 / width:1024`（§3.2 测算的基准） |
| 未处理 `appRestoredResult` | ❌ **缺失，且是官方明文要求**。Capacitor 文档：「because the Camera API launches a separate Activity... **you should listen for `appRestoredResult`** in the App plugin to handle any camera data... in the case your app was terminated by the operating system while the Activity was running」。**不处理会同时丢照片和打卡**。§3.1 已把它列为"必须处理的边界" |
| `resultType: Base64` + 存 IndexedDB | ⚠️ 两处都不建议。官方最佳实践写的是 `resultType: Uri, // Not Base64 for large images`（Base64 标注 "Memory intensive"）。IndexedDB 的问题见 §3.2 与 11.3 |
| 未提「要新装 `@capacitor/filesystem`」 | ⚠️ 现有插件只有 `@capacitor/app` 与 `@capacitor/local-notifications`，FileSystem 需新装 + `cap sync` |

**我方替代路径（更省内存）**：`getPhoto({ resultType: Uri })` 拿 `photo.path` → `Filesystem.copy({ from: photo.path, toDirectory: Directory.Data })`。
**全程不经过 JS 层、不产生 base64 字符串**，比"先转 base64 再写文件"更稳，也避开大字符串过 bridge 的内存压力。

### 11.2 层次 2「本地识别药片」—— **不建议做，而且在这个插件上做不了**

这一层是整份方案最需要纠正的部分。四条都有官方文档的直接反证：

| # | 方案原文 | 官方文档的实际说法 |
|---|---|---|
| 1 | 「药片通常会**命中 Home good** 或被识别为圆形物体」 | ❌ **不成立**。Capawesome 官方 FAQ：base 模型只分 **5 个粗类别**（Fashion good / Food / Home good / Place / Plant），且「**Any object that does not fall into one of these categories receives no label**」。药片大概率**拿不到任何标签** —— 不存在"因为圆所以命中"的机制 |
| 2 | 「用 ML Kit 的 **Custom Model API 加载自定义 TFLite**」 | ❌ **不成立**。官方 FAQ：「The plugin uses the base object detection and tracking model, which is bundled with the app. **Custom TensorFlow Lite classifier models are currently not supported.**」→ 方案里的"路线 B"在这个插件上**根本走不通** |
| 3 | `npm install @capacitor-mlkit/object-detection` | ⚠️ **版本不兼容**。官方兼容表：插件 `8.x.x` → 要求 **Capacitor >= 8.x.x**；且 `processImage` 是 **8.2.0** 才引入的（该插件属于 8.2.0 新增的 14 个插件之一）。**本项目是 Capacitor 6.1.2**，没有可用版本 → 要用就得跨 **6 → 7 → 8** 两个大版本升级，还要重测自研的 `AppSettingsPlugin` |
| 4 | `objects.some(o => o.labels.some(l => l.confidence > 0.6))` | ❌ **逻辑无效**。这等于"**检测到任何物体且置信度 > 0.6 就算拍到药**" —— 对着食物、植物、家具都会返回 true。另外返回值应是 **`detectedObjects`**（不是 `objects`），且 `ProcessImageOptions` **没有 `detectorMode` 这个参数** |

**结论与 §9.2 一致：不做药物识别（L3/L4）。** 现在还多了独立证据 —— 即便愿意付升级成本，这个插件也**只输出 5 个粗类别、且不支持自定义分类模型**，拿不到"这是药片"这个判断。

### 11.3 层次 3「存储管理」—— 方向对，三处与已拍板决策冲突

| 条目 | 核实结论 |
|---|---|
| 「你在 `boot()` 里**已经有跨天检查**的 `setInterval`」 | ✅ **说对了**（这条纠正我自己）。`app.js:1439-1443` 确有 30 秒轮询的跨天刷新：`if (todayKey() !== lastDay) {...}` |
| 「定期自动清理（**建议保留 30 天**）」 | ❌ **与已拍板决策冲突**。D-1 刚定为「**不做自动清理**，改为用户自选保留期（90 / 180 / 365 / 不清理，默认不清理）」。且 **30 天对服药记录太短** —— 依从性追踪通常要看 90 天以上。**照片 30 天可以，记录不行，两者保留期应分开** |
| 照片存 IndexedDB | ⚠️ 除 §3.2 已列的理由（配额与淘汰策略不可控）外，还有一个**新引入的一致性问题**：**照片进 IndexedDB 后，D-1 的 `STORAGE` 卡就统计不到照片占用** —— 用户看到的"已用 X KB / 5 MB"会**变成错的**，而那张卡的全部意义就是让容量可见。**照片必须走 `Directory.Data`，并让 `storageStats()` 一并统计照片目录** |
| 「把 `purgeOldPhotos()` 挂在 boot 的 `setInterval` 里就行」 | ⚠️ **有缺口**。App 在后台时 JS 定时器会被系统暂停 —— 用户长期不开 App，清理就不执行。应**在启动时也跑一次**（与 D-1 的 `gcNotified()` 同一位置），定时器只作补充 |

### 11.4 整份方案没涉及、但已经拍板的两件关键事

| 缺失项 | 为什么关键 |
|---|---|
| **拍不了的时候怎么办** | 这是**已拍板**的设计点（**方案 B：可跳过但留痕 + 统计跳过率**）。现实中拍不了的场景很多：在外面、开会中、药盒没带、光线太暗、存储满、相机权限被误关、老人不会用相机。**不定义这条，用户遇到就只能强停 App 或卸载 → 数据断掉，比不强制更糟。** 它比识别算法重要得多 |
| **PIPL 合规** | 医疗健康属敏感个人信息。**强制收集比可选收集更难辩护"必要性"**（第 6 / 28 条）。纯自用可依第 72 条豁免；一旦上架或给照护者看，就要做事前影响评估（第 55 条）、单独同意（第 29 条）等，见 §4 / §6 |

### 11.5 可以采纳的三点

1. **`correctOrientation: true` 提升为"必开"** —— §3.1 已把它列为参数之一，但值得强调：不加这个，Android 上竖拍的照片可能横过来。
2. **「识别到药片后弹确认框、而非静默打卡，保留用户最终控制权」** —— 这个原则是对的（误触发必须由人兜底）。我们做 L1/L2 时是同一原则：**宁可放行，不可误伤**。
3. **「先做层次 1，识别单独开分支慢慢迭代」** —— 与 §9.6 的实施顺序一致。

### 11.6 一句话结论

**层次 1 可采纳（补 `appRestoredResult`、改 `Uri` + `FileSystem`）；层次 2 不做（官方文档已排除该插件做药物识别的可能）；层次 3 按 D-1 已拍板的方案走，不引入自动清理。**
