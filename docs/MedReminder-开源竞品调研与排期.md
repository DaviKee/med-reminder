## 0. 排期（2026-09-23 按「重要性 × 工程难度」重排）

### 0.1 排序原则

1. **重要性优先**；同档重要性下，**难度低的先做**。
2. **杠杆项提前** —— 成本极低、但能降低后续**所有**改动验证成本的，允许插队（本例：H-4 `npm test`）。
3. **依赖不能倒置** —— 被阻塞项不得排在其前置之前（H-3 阻塞 S-1；S-1 阻塞 S-2 / S-6）。
4. **去风险前移** —— 可能**推翻技术选型**的调研（S-0）必须排在大批功能之前，否则返工成本翻倍。
5. **待拍板项不占排期位** —— R-1 / S-8 / Q1 单列，取决于业务决策而非工程难度。

## 2. ★ 我核实出的真实缺陷（文档 §6.1 命中 3/4）

### H-1 固定时刻**只改时刻不重排**（真 bug，我上一轮漏了）

**证据**（`app.js` 的 `saveMed`）：

```js
var modeChanged = prevMode !== medModeDraft;
var intervalChanged = !isFixed && m.interval !== stepVal;
...
if (modeChanged || intervalChanged) rebuildTodayDoses(m);
```

场景：药品**已经在固定时刻模式**，用户只把时刻从 `08:00/20:00` 改成 `09:00/21:00`：

- `modeChanged` = false（模式没变）
- `intervalChanged` = `!isFixed && ...` = **false**（固定模式下这一项恒定 false）
- → **`rebuildTodayDoses` 不执行**

而随后的 `ensureFixedDoses()` 是幂等的（"已有该药剂量就只 reindex 后返回"）→ **也救不了**。

**后果**：改了时刻，**今天页显示的还是旧时刻、系统通知也是旧时刻**，要等次日才生效。用户会认为"改了没保存"。

**为什么我漏了**：上一轮 `fixed.spec.js` 测了 `fixed ↔ interval` 切换（那会触发 `modeChanged`），**没测"fixed 内部改时刻"**。这是测试用例的盲区，不是逻辑天真。

---

### H-2 `sw.js` 三层问题（比文档说的严重）

文档只说"离线资源问题"，实际是三层：

| # | 问题 | 证据 |
|---|---|---|
| 1 | `ASSETS` 预缓存清单**漏了两个文件** | 只列了 `app.js` / `notify.js`；实际有 `photo.js`、`backup.js` —— **新加的文件从没同步进这个清单** |
| 2 | `fetch` 是 **cache-first 且永不回源** | `caches.match(req)` 命中就直接返回，不发请求；`CACHE = 'medreminder-v2'` 是**手写常量**，改代码时不会自动变 |
| 3 | 注册失败**完全静默** | `register('sw.js').catch(function () { /* ignore */ })` |

**第 2 条是要紧的**：如果 WebView 里 SW 生效，**更新 App 后仍可能读到缓存的旧 `app.js`** —— 表现就是"装了新版但功能没变"。这和我们已经吃过两次的"装了旧版"是同一类困惑（一次是 `serve-apk.py` 缓存旧包，一次是手动拷错文件）。**在诊断上，这类"幽灵旧代码"最耗时间。**

**我的建议（明确取舍，不是列选项）**：

> **原生环境（Capacitor）下干脆不注册 SW。**

理由：APK 里所有资源都在 `assets/public/`，**离线本来就成立**，SW 收益 ≈ 0；而 stale-cache 风险 > 0。PWA（浏览器打开）场景保留即可 —— 用 `Capacitor.isNativePlatform()` 分流。

同时**仍然要修** `sw.js` 本身（补齐 ASSETS + 版本号与 `APP_VERSION` 联动 + 改 network-first 或至少 `stale-while-revalidate`），因为浏览器场景还在用，且这是个"下次还会踩"的坑。

### H-3 备份导入校验**只覆盖了一半**（文档说对了，我给具体清单）

`parseBackup()` 对 `meds` 校验得很细（id/name/interval/mode/times 全查），但 `doses`：

```js
if (!o.data || !Array.isArray(o.data.meds) || !o.data.doses || typeof o.data.doses !== 'object')
```

—— **只判断"是个 object"，内部字段零校验**。具体缺口：

1. **日期 key 格式**未校验（`YYYY-MM-DD`）→ 脏 key 会让 `historyDays()`、依从率统计走偏
2. **每条剂量的 `time` 未校验**：非数字会直接进排程 —— `for (t = done[0].time; t < 1440; t += step)` **要么死循环、要么排 0 次**
3. `status` 未校验枚举值（`pending/taken/skipped`）→ 统计直接漏项
4. `idx/total` 未校验 → 界面出「第 NaN / undefined 次」
5. **无体积上限** → 超大 JSON 会卡住 UI 线程（主线程同步 parse）
6. **无防重复导入** → 同一个备份导两次，剂量直接翻倍（属于数据损坏，且用户不会察觉）
7. `id` 未做**唯一性**校验 → 重复 id 会让 `medById` 返回第一个、通知取消错对象

**这条必须先做**：S-1/S-2 马上要往 `med` / 剂量里加新字段，**校验不补上，新字段进来全是裸奔**。

## 4. ⚠️ 与鸿蒙移植的交互（这份材料里它完全没考虑）

已完成的鸿蒙调研（`MedReminder-鸿蒙移植调研.md`）结论要叠加进来看：

| 文档推荐的 | 与鸿蒙的关系 |
|---|---|
| 通知操作按钮（它列为我们的**优势**） | ⛔ **鸿蒙侧不支持 `localNotificationActionPerformed`** → 锁屏按钮会「点了没反应」。**不要再在这个能力上加深投入**；S-2 的库存扣减必须挂在"进 App 打卡"上（本来也是这么设计的，确认即可） |
| 家庭照护远程 | ⛔ 需要账号 + 云，与本地优先定位冲突（见 §5） |
| S-7 报告导出 | ⚠️ 若用 PDF 库 → 引入原生依赖、鸿蒙要重做；改用"打印友好 HTML" |
| S-5 明暗主题 | ✅ `prefers-color-scheme` 在 WebView 通用，双端无碍 |
| Tier 1 全部 | ✅ **纯 web 层，移植时零改动** |

**由此得出一条纪律（建议写进项目约定）**：

> **任何新功能都不得把平台差异带出插件层。**
> 双端同步的成本，只取决于这一条守不守得住。

---

## 5. 明确不采纳（以及为什么）

| 事项 | 不做的理由 |
|---|---|
| **AI 症状分析 / 健康教育 / 急救指导** | ① **医学责任边界** —— 给出建议就要承担后果；② 我们**没有模型通道**（云端服务只面向浏览器前端，CLI 不可用，且本机无任何模型凭据）；③ 误判的代价远高于收益。文档自己也建议早期别做 —— **我同意，而且是永久不做，不只是"早期"** |
| **Firebase 登录 / 云数据库 / 远程同步** | 与我们的根本定位冲突：**本地优先、无账号、数据不出手机**。这正是能让家里老人放心装的前提。一旦上云，隐私设计、账号体系、离线冲突合并全部要重做 |
| **家庭照护远程查看 / 紧急联系人** | 需要账号 + 云 + 权限三层。**用 S-7 报告导出替代** —— 医生/家属真正需要的是"近 7 天有没有按时吃药"这一个答案，一份报告就够 |
| **硬件提醒器 / 桌面提醒扩展** | 它是另一个产品（固件 + PCB），不是这个 App 的迭代方向。**但它的洞察我认可**：手机通知对不用手机的老人确实不可靠 —— 这一点我们用 S-7 报告 + 拍照凭证去补 |
| **DoseBot 的"旅行计算器"** | 场景不符（解决跨时区服药），我们用户不需要 |
| **F-Droid / 上架分发** | 不是不采纳，是**被 R-1 阻塞** —— 签名密钥不可逆，要先定发布渠道 |

## 6. 排期（融合鸿蒙迁移）

```
阶段 0  鸿蒙可行性 spike（建议插在最前）
        ↑ 把现有 www/ 塞进 @capacitor-ohos 最小工程，验证 4 个插件真能跑
        ↑ 理由：它决定后面所有技术选型。别等做完一堆功能才发现某插件不可用
        ↑ 需要先装环境（DevEco Studio + SDK，路径不能有中文）

阶段 1  H-1 ~ H-4（清掉真 bug 与基础设施）→ v1.4.2
        理由：其中 H-1 是真 bug；H-3 是 S-1/S-2 的前置

阶段 2  S-1 → S-2（剂量 → 库存）→ v1.5.x
阶段 3  S-5（主题）→ S-3/S-4（周期/疗程）→ v1.6.x
        理由：主题尽早做，避免两套工程重复改 CSS

阶段 4  S-6（可视化）→ S-7（报告导出）→ v1.7.x

阶段 5  鸿蒙适配落地（harmony 分支）
        此时 Tier1/Tier2 已是纯 web 层成果，只移一次

——  S-8 多语言、R-1 签名、Q1 记录保留期：待拍板
```

**为什么不先做鸿蒙适配再做功能**：Tier 1/2 全是 web 层，语**双端共享一份 `www/`**。先做功能再移植 = **只移一次**；先移植再做大功能 = 每次都要在两个工程里同步改，成本翻倍。

**唯一例外是阶段 0**：spike 必须先做，因为它可能**推翻技术选型**（万一某插件在鸿蒙上不可用，S-2/S-7 的实现方式就要改）。

## 7. 这份材料总评

**值得采纳，但不是照单全收。**

- **它最大的价值**是 §6.1 —— 四条待修里三条是真缺陷，其中 **H-1（固定时刻改时刻不重排）和 H-3（doses 校验为零）是我自己漏掉的**。这说明让第三方读一遍代码是有用的。
- **它的功能清单方向正确**：库存、剂量、周期、疗程都属于"从提醒器走向用药管理"的正路，而且**恰好全是 web 层，与鸿蒙移植零冲突**。
- **它的主要缺欠**：完全没考虑鸿蒙迁移；把"通知操作按钮"当纯优势（鸿蒙上会失效）；低估了我们已有的发布/验收工具链。
- **它建议排除 AI 与云**，我完全同意 —— 但我要更进一步：**这两项不是"早期不做"，而是与产品定位根本冲突**。

## 四、关键发现

### 4.1 你的功能位次

**已达标的（与头部持平）**
- 精确闹钟 + 息屏/锁屏提醒：与 medTimer、MediTrack 同级
- 锁屏操作按钮：你在原生层就有，属于多数竞品有的"基本盘"
- 重启恢复（BootReceiver）：与 MediTrack 的"重启/OTA/时区变更重排"同级

**明显落后、且多个竞品都有（应补）**
1. **数据导出 / 备份**：medTimer（CSV + JSON）、HomeCare（CSV/FHIR/PDF）、MediTrack（分享文本）、remedmind（CloudKit）——**这是行业基本盘，你 0 覆盖**
2. **库存 / 余量预警**：medTimer、remedmind、HomeCare、MediTrack 都有
3. **漏服可见化**：MediTrack 自动标记、iOS 老年向 1 小时宽限、my-med-timer 热力图
4. **无障碍**：iOS 老年向项目给出了可直接抄的规范（字号 `.title3` / 行高 60pt / VoiceOver / 权限被拒引导）
5. **特定星期 / 周期用药**：medTimer 的 break period、`OpenPillReminder` 专做避孕药自动暂停——你的"固定间隔"模型覆盖不了

**你的差异化（少数竞品才有的）**
- **打卡制（首次打卡起算后续剂量）**：多数竞品是"固定时刻表"，你是**事件驱动的滚动排程**。这在"服药时间不固定、按需起算"的场景确实有独特价值——但也最容易让用户困惑（见 4.2）
- **原生 / 浏览器双层降级**：PWA 类项目要么纯前端（后台不可靠）、要么纯服务端推送（依赖联网 + 后端）；你两者都有
- **零依赖纯 JS + 自成一套设计系统**：工程极轻，改造成本低

### 4.2 最值得借鉴的 8 个具体做法

| # | 做法 | 出处 | 对你的价值 |
|---|---|---|---|
| 1 | **导出 + 备份恢复**（CSV 历史 / JSON 备份） | medTimer | 直接补齐你的 P0 #3 |
| 2 | **药品名自动补全**（接 FDA Drug API / 药品库） | sinha-19 MedTrack | 替代"预置假药"，同时提升录入体验（P0 #1） |
| 3 | **老年向无障碍规范**：最小 `.title3`、行高 60pt、全 VoiceOver、权限被拒 Banner 直达设置 | yangg1224 MedTrack | 直击你的 P0 #2 / P1 字号与触摸区 |
| 4 | **漏服"惰性对账"**：回前台时把"到点 +1h 未处理"记为 missed，不做不可靠后台任务 | yangg1224 MedTrack | 与你的 P1 漏服问题同解，且实现成本低 |
| 5 | **漏服 60 分钟自动标记 + 补记** | saadkhan2003 MediTrack | 让漏服可见、可补 |
| 6 | **库存追踪 + 余量耗尽预测** | medTimer / remedmind / HomeCare | 你完全没有的一块，且是高频真实痛点 |
| 7 | **闹钟型提醒（静音也响）+ 周末模式 + 休息期/特定星期** | medTimer | 提升排程模型的表达力 |
| 8 | **权限被拒的显式引导**（Banner + 直达设置） | yangg1224 MedTrack | 你浏览器模式权限被拒时无任何提示（P1） |

### 4.3 需要注意的反面教材

- **纯 PWA 做不到可靠的后台提醒**：`ciortanmadalina/medication` 不得不引入 Netlify Functions + 服务端调度器（每 5 分钟）+ VAPID 推送，才实现"App 关闭也能响"。**你选择"Capacitor 原生壳 + 本地精确闹钟"是正确的技术判断**，别被 PWA 的轻量迷惑回去。
- **Flutter 阵营普遍依赖 FCM 服务端推送**：换来了跨端一致性，代价是必须有后端、必须联网。
- **"预置示例数据"是通病还是反例？** 你注入了真实感很强的假药（阿莫西林/维生素 D3）却无"示例"标识；相比之下 `sinha-19` 用真实药品库、`rajanarahul93` 用空白引导。→ 你应该走**空白态 + 引导**或**真实药品查询**。

## 五、建议路线图（与既有 UX 评审对齐）

**第一批（P0，高影响低成本）**
1. 去掉预置假药 → 空白态引导；可选接入药品名查询
2. 删除 `user-scalable=no`；正文 ≥16px；触摸区 ≥48pt
3. **新增"导出记录"（CSV / 分享文本）+ 本地备份恢复**（对齐 medTimer）
4. 空态补"打卡制"因果说明 + 首启 1 步引导

**第二批（P1，值得排期）**
5. 漏服显式化（到点 +N 分钟自动标记 + 可补记）
6. 权限被拒 Banner + 直达设置
7. 浮层可访问性（`role="dialog"` / 焦点管理 / Esc）
8. 适配 reduced-motion；状态不只靠颜色

**第三批（P2，长期）**
9. **库存 / 余量预警**（多个竞品标配，你缺）
10. 特定星期 / 周期用药（避孕药等）
11. PRN 按需药；渐进式提醒强度
12. iOS 工程（可参考 `xtool` 在非 macOS 上开发 iOS 的路线）；i18n；单测与 CI

## 5. 对照 MedReminder：这张全景图告诉你什么

### 5.1 你已经在第一梯队的地方
- **提醒内核**：精确闹钟 + 锁屏操作 + 重启恢复，与 medTimer 同档。
- **"打卡制滚动排程"**：多数竞品是固定时刻表；你的模型更接近 medTimer 的"following dose"，但更轻。
- **零后端、纯本地、离线可用**：与 medTimer 的"full offline privacy"同一价值主张，且你连依赖都更少。

### 5.2 全景图暴露出的"空白格"（按"竞品普及度 × 你的成本"排序）

| 优先级 | 空白 | 竞品普及度 | 你实现成本 | 为什么值得做 |
|---|---|---|---|---|
| **P0** | 导出（CSV/PDF）+ 备份恢复 | ⭐⭐⭐⭐⭐ 头部全有 | 低（纯前端） | 你唯一"完全空白且头部标配"的一格；也是你 UX 报告的 P0#3 |
| **P0** | 首启"假药"种子数据 | —— | 极低 | 无标识假数据在服药场景是信任/安全问题 |
| **P0** | 禁止缩放 / 字号 / 触摸区 | ⭐⭐⭐⭐ 老年向标配 | 极低（1 行 + CSS） | 目标用户是长者，无障碍是硬门槛 |
| **P1** | 漏服显式可见（含 +1h 惰性对账） | ⭐⭐⭐⭐ | 低 | 现在静默吞掉漏服，用户永远不知道 |
| **P1** | 库存追踪 + 低库存提醒 | ⭐⭐⭐⭐ | 中 | 与"打卡制"天然契合（每剂扣减） |

| **P2** | 多成员 / 照护者 | ⭐⭐⭐ | 高 | 需要架构改动（当前单用户本地模型） |

| **P3** | 条码扫描 / 药品库 | ⭐⭐ | 中 | 可替代"预置假药"，是优雅解法 |

### 5.3 三条策略性结论

1. **你的技术路线是对的，别被 PWA 的轻量迷惑回去。** 本轮再次验证：纯 PWA 项目（SymptomSync 用 Supabase Cron、MedSync-AI 用 Socket.IO）在"后台可靠提醒"上都得额外加服务端调度器或推送，且 SymptomSync 自己在 README 里承认 *"窗口失焦或网络慢时提醒可能不显示"*。你选 Capacitor 原生壳 + 本地精确闹钟，绕开了这整类问题。

2. **赛道下一站是"可带走 + 可协作"，不是"更多提醒花样"。** medTimer 的功能集已接近成熟（PR 流以修复/依赖为主）；而 damacus 与 HealthLog 的热点全在**数据可带走（报告/导出/FHIR）、照护者协作（委托/审计）、暂停期建模**。你现在连"数据可带走"都是 0，这是最大的结构性缺口。

3. **老年向无障碍是你必须补的短板，且抄得到现成规范。** 队列里有一整批"超大字 + 语音 + 照护者告警"的项目（Eldora/CareCue/bolo/sweet-pill-reminder），加上 yangg1224 系 iOS 的老年向规范（最小字号、≥60pt 可点行、全屏阅读器、权限被拒直达设置）。这些是可以直接照搬的**设计约束**，成本低、收益大。

## 4. 你目前缺失或可以增强的功能



### 4.1 药品库存管理

这是非常值得加入的功能。



参考项目中，DoseBot 已经有库存管理概念。



你现在的功能主要只看：

- 药品名

- 间隔

- 时间



但缺少：

- 当前剩余数量

- 每次用量

- 低库存提醒

- 预计什么时候用完

- 补药提醒



建议扩展数据结构：

```js

{

  id: "...",

  name: "降压药",

  interval: 8,

  doseAmount: 1,

  stock: 30,

  lowStockThreshold: 7

}

```



然后在用药时实时扣减库存，甚至提醒用户“3 天后可能用完”。



---



### 4.2 剂量管理

你当前没有完整的“服药剂量”维度，缺少：

- 每次几片 / 多少毫升

- 单位（片、粒、毫升）

- 饭前 / 饭后 / 睡前

- 备注说明



建议增加：

```text

剂量：1

单位：片

服用说明：饭后

备注：不要和某药同时服用

```



这种功能会让你的应用比“简单提醒器”更接近“真实用药管理”。



---



### 4.3 周期规则

当前大多是“每天提醒”，但真实用药有很多规则，比如：

- 每周一、三、五

- 仅工作日

- 每隔N天

- 指定日期范围

- 疗程开始和结束日期



建议最先支持一份简化版本：

- 每天

- 每周指定星期

- 仅一次

- 指定日期范围



---



### 4.4 疗程管理

你可以加入：

- 疗程名称

- 开始日期

- 结束日期

- 每天多少次

- 是否自动停用



例如：

```text

疗程名称：抗生素疗程

开始日期：2026-09-20

结束日期：2026-09-27

每天 2 次

```



这样就不必用户手动删除药物。



---



### 4.5 多语言

目前项目主要是中文界面，建议未来支持：

- 简体中文

- 繁体中文

- 英语



建议逐步把字符串抽离，以便后续国际化。



---



### 4.6 明暗主题

DoseBot 已经将“明暗主题”作为产品亮点。



你的应用目前以深色为主，建议未来增加：

- 深色模式

- 浅色模式

- 跟随系统



对老年用户尤其要提高可读性：

- 高对比度

- 明确的状态颜色 + 文本 + 图标



---



### 4.7 家庭照护 / 共享模式

参考项目 `cuida` 更强调照护场景。



你目前是单用户本地模式，缺少：

- 家庭成员

- 照护者视角

- 远程查看

- 紧急联系人

- 远程提醒



注意：这部分肯定会引入更大复杂度，需要账号、权限、云端和隐私设计。



建议先做一个更安全的中间方案：

- 导出最近 7 天记录

- 导出 CSV / PDF 给家属或医生

- 生成报告



这比直接做云端同步更稳妥。



---



### 4.8 数据可视化

你已经有依从率，但还可以增强：

- 月历视图

- 每周统计

- 每月统计

- 漏服时间段统计

- 实际服药时间和计划时间差异

- 用药趋势



这会让用户更容易发现规律，而不仅仅看“今天是否打卡”。

# 第五部分 · 华为应用市场商业竞品调研（2026-09-29 新增）

> ⚠️ **本部分是前四部分的一个空白填补。**
> 前四部分盘的是 **GitHub 开源项目**（medTimer 等）——那些是"同类实现"，不是"我们用户真会装的 App"。
> 本部分盘的是 **华为应用市场上真实在售/在用的商业应用**，包括手机端与手表端。
> 数据来源：各应用官网、百度百科、下载站页面、华为官方支持文档（详见文末）。**均为公开信息，未经实测。**

## 一、结论先行（三句话）

1. **这个赛道已经很挤，而且华为生态里有人做得比我们深。**
   药管家是华为官方认证的生态合作伙伴（余承东发布会点名），元服务上线单月用户破千万。
2. **但没有任何一家做到「本地优先 + 无账号 + 数据不出手机」。**
   全部走"账号 + 云同步 + 家庭协同"路线，这恰恰是**我们明确不做的**（产品定位 §4.2）。
3. **手表端是所有人的战场，也是我们最大的空白。**
   药管家、叮当快药都已上手表；华为自家运动健康也有服药提醒。**我们目前完全没有手表端。**

## 二、手机端主要竞品

### 2.1 药管家（元向量智能科技）—— **生态最强者**

| 项 | 内容 |
|---|---|
| 开发者 | 元向量智能科技（东莞）有限公司 |
| 版本 | **1.7.2**（2026-07），62.62 MB |
| 平台 | iOS / HarmonyOS / Android / **手表** / 电脑 |
| 评分 | **5.0** |

**核心功能**：

- **用药提醒**：自定义服药时间、**剂量**、重复模式；**可关联家人账号远程提醒 + 查看记录**
- **智能核对系统**：识别**过期药品**、**配伍禁忌**并提供实时预警 ⭐（这是我们完全没有的能力）
- **药品管理**：拍照识别药名、分类药箱、**过期提醒**、**库存阈值提示**（买药提醒）
- **健康指标**：体重 / 血压 / 血糖 + 历史趋势图
- **电子病历**：个人与家庭成员病历，上传处方单、检查报告
- 复诊提醒、喝水提醒、桌面卡片

**华为生态地位（这点最关键）**：

- **2022 华为年度原子化服务**上榜
- **2023 华为开发者大会**获华为颁奖，**余承东在主题演讲中介绍了药管家元服务**
- 基于 HarmonyOS 的**元服务版本**（桌面卡片形态、**免安装**），**上线单月用户量破千万**
- 受邀在华为开发者日（HDD）分享

> ⚠️ **对我们的意义**：药管家是"华为生态官方样板"级别的存在。
> 它把**药品管理 + 库存 + 过期 + 配伍禁忌 + 病历 + 家人协同 + 手表 + 元服务**全做了，
> 而且做成了**元服务**（我们连 App 都还没移植过去）。
> **正面拼功能我们拼不过它** —— 我们的机会只可能在"**不联网、不注册、数据不出手机**"这个它做不到的定位上。

### 2.2 爸妈的药盒（个人开发者 王利航）—— **定位与我们最像**

| 项 | 内容 |
|---|---|
| 开发者 | **个人开发者**（王利航） |
| 版本 | **1.2.0 / 1.2.1**（2026-08），90.60 MB |
| 平台 | Android / **HarmonyOS 已上架华为应用市场** |
| 评分 | 8.9 |

**核心功能**（与我们高度重合）：

- **定时提醒**：到点推送；**可 TTS 念出药名** ⭐；**App 被清理后仍尽量按系统闹钟准时送达**
- **一键打卡**：点一下记录已吃，**长按可撤销** —— 这正是我们 v1.4.x 做的交互
- **延后 30 分 / 今日跳过** —— 对应我们的 snooze / 跳过留痕
- **家人协同**：绑定家庭，子女看进度；**漏服时提醒子女 + 一键拨号**
- **拍照录药**：拍药盒/说明书，**端侧 OCR 识别药名**；**扫条码回填** —— 对应我们的拍照打卡（但**他们的拍照是为了录药，我们是为了留痕**）
- **用药报告**：近 30 天打卡日历 + **生成分享海报** —— 对应我们规划中的 S-7
- **桌面卡片**：显示下次吃药时间与今日进度
- 药品**快过期时提醒子女**

**开发者的产品思考（值得我们读，原文见来源）**：

> 「问题不是闹钟，是**家庭分工**。难的是：谁维护药品清单（往往是子女）／谁执行打卡（必须是爸妈，步骤要少）／漏服时信息如何回到子女侧。」
>
> 「界面做成『今日药盒』**分格**，而不是表格和图表。老人认知成本更低，子女讲解也快：『跟家里那个格子盒一样，点一下就行。』」
>
> **能力边界（刻意收窄）** —— 做：提醒/打卡/家庭同步/可选重复提醒、端侧 OCR 辅助录药、延后/跳过/月报。
> **不做**：**问诊、处方、卖药、疗效承诺**、宣称识别率替代人工核对、全家药柜、多家庭中台。

> ⚠️ **对我们的意义（这是本次调研最有价值的一条）**：
> ① 它证明**"个人开发者 + 适老化单一场景"这条路走得通** —— 不靠云、不靠生态也能上架；
> ② 它的**"做/不做"清单与我们产品定位惊人一致**（都不做问诊卖药），说明我们的克制是对的；
> ③ **但它比我们多了：语音播报、条码扫描、家人协同、桌面卡片** ——
>    其中**桌面卡片**和**语音播报**是适老化的硬需求，我们**完全没有**。

### 2.3 华为运动健康 · 健康三叶草 —— **系统级免费替代**

华为**系统自带**能力，可能是我们最被动的竞争对手：

- 服药提醒：设服药时间、**药品名**、**备注**
- **手机端 + 穿戴设备端双端推送**（**计划时间前后 15 分钟**）
- 手机状态栏提醒 ／ 手表**振动 + 文字**提醒
- 支持**周报**与分享到微信/微博

> ⚠️ **对我们的意义**：**这是免费的、系统级的、双端的**。
> 用户如果只需要"简单提醒"，**装我们不如用系统自带**。
> 我们的价值必须建立在系统自带做不到的地方：**打卡制滚动排程、拍照留痕、依从率统计、固定时刻不顺延**。

### 2.4 叮当快药 —— **手表端先行者**

- 2021 年随 HarmonyOS 2 / WATCH 3 发布，**手表端内置"吃药提醒"**
- 路径：**手表应用市场**搜"叮当快药" → 安装 → **手表侧同步设置提醒**
- 主业务是**在线问诊 + 28 分钟送药**（用药提醒是引流功能）

| 周期/疗程规则 | ⚠️ | ✅（疗程） | ✅（重复周期） | ❌（= S-3/S-4） |
| 健康指标 / 病历 | ✅ | ❌ | ⚠️ | ❌ **不做** |
| **不需要账号/不联网** | ❌ | ❌ | ⚠️ | ✅ **独特** |

## 五、这次调研给我们的四个判断

### 5.1 我们真正的护城河只剩一条：**本地优先、无账号、数据不出手机**

功能上我们**全面落后**（剂量、库存、过期、语音、卡片、手表、报告、录药 —— 全缺）。
但**没有一家商业竞品做"不联网、不注册"**。这是我们唯一的结构性优势，且**与产品定位完全一致**。
→ **建议：把这个定位在应用描述里写得更显眼**，而不是靠功能清单去拼。

### 5.2 排期表得到了外部验证

我们排的 **S-1（剂量）→ S-2（库存）→ S-7（报告）**，**恰好是竞品全都有的"基本盘"**：

- **S-1 剂量/单位/备注** —— 药管家有、系统有、手表原生有 → **不补就是不及格**
- **S-2 库存/过期** —— 药管家和爸妈的药盒都有，且**直接解决"药吃完了才想起来"**
- **S-7 报告导出** —— 爸妈的药盒有分享海报、系统有周报 → 我们有依从率数据却没出口

→ **排期方向是对的，而且优先级应该更高**（这三项从"改进"变成"缺了就不合格"）。

### 5.3 三个"新发现"的缺口（此前未列入排期）

| 缺口 | 谁做了 | 为什么重要 |
|---|---|---|
| **桌面卡片（widget）** | 药管家、爸妈的药盒、系统 | 适老化核心：**不打开 App 就能看到下次吃药时间** |
| **语音播报药名（TTS）** | 爸妈的药盒 | 老人**看不清屏幕也能知道吃哪种药**，比提醒本身更关键 |
| **手表端**（通知/打卡） | 药管家、叮当快药、系统 | 手表振动是**最不容易被忽略**的提醒方式 |

> ⚠️ 前两项**都是 web 层无法独立完成的**（依赖原生能力）→ 与鸿蒙移植强耦合，
> **建议放进 S-0 spike 的验证清单**（特别是"通知能否在手表上振动"）。

### 5.4 一个警告：别被功能清单带跑

爸妈的药盒作者的原话值得抄下来：

> **「能力边界（刻意收窄）」** —— 明确列了"不做"的清单，且**刻意不做问诊、处方、卖药、疗效承诺**。
> 讨论主题之一就是「**如何避免『功能堆满却没人用』**」。

→ 我们接下来补 S-1/S-2/S-7 是**补基本盘**，但**不要**因此去追"配伍禁忌识别""健康指标""电子病历"——
那些是**药管家的赛道**（它有医院资源与生态位），**不是我们的**。
